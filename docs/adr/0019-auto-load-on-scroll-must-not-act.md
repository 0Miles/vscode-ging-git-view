# 捲動自動載入留下來,但它不得產生操作級的副作用

`ging-git-view.history.loadMoreOnScroll` 保留。捲動接近底部時自動載入下一頁 commit 是**瀏覽**的延續,所以它必須與瀏覽無異:不關閉展開的 Commit Details View、不弄丟鍵盤焦點的錨點、不讓畫面在使用者眼前跳動。它撐大的 **loaded commit window** 必須看得見,而且有路縮得回來。守不住這幾件事的自動載入,不該存在。

這段程式碼自 webview UI 引進(`7824be6`)以來一個字沒改過,從未被測試涵蓋,也從未出現在 CHANGELOG 或 README。這篇 ADR 是它第一次被真正決定。

## 為什麼未來的讀者會困惑

**「自動載入不就是把按鈕自動按一下嗎?」** 不是,而這正是舊實作錯在哪裡。按鈕被按下是一個**操作**:使用者換了工作焦點,順手關掉展開的細節、把焦點交還給重繪後的表格,都還說得過去。捲到底則是**瀏覽**:使用者什麼都沒要求。兩者共用同一個函式,就等於讓瀏覽長出操作的副作用 —— ADR-0014 花了整節論證的「捲動是瀏覽,方向鍵是操作」,在這裡被反過來破壞了。

**與 ADR-0014 的張力是這篇 ADR 的主題,不是它的副作用。** 鏈條是:方向鍵移動焦點會呼叫 `scrollIntoView`,那本身就發出 scroll 事件 → 門檻成立 → 自動載入 → 整表重繪,持有焦點的列被銷毀 → `focusedRowIndex` 找不到 activeElement,退回它的 fallback 錨點,也就是展開中那一列 → 而那個錨點剛剛被同一條路徑上的 `hideCommitDetails()` 清成 null → 回傳 −1 → 下一次方向鍵從第一列開始。**使用者用方向鍵走到第 300 列,自動載入觸發,再按一次下鍵,人在第 1 列。** 所以焦點錨定不是加分項,是這個功能能否存在的前提。

**畫面跳動的來源不是重繪,是 `hideCommitDetails()`。** 在真實 Chromium 量過:整表 `innerHTML` 抽換本身**保得住**捲動位置 —— 內容只往下長,既有偏移量仍然有效,同一列停在同一個像素(量到位移 0px)。但若展開的 CDV 位於視窗上方而重繪時被移除,`scrollY` 不變、內容卻往上跑了整整一個 CDV 的高度(量到 253px,約 10 列)。所以「載入前記下 `scrollY`、載入後還原」對這個跳動**完全無效**:瀏覽器本來就停在那個位置,還原等於原地踏步。唯一有效的修法是不要移除那一列。這個跳動是 inline 模式獨有 —— docked 的 CDV 是 `position: fixed`,不在文件流內。

## 考慮過但否決的方案

**整個刪掉,只留按鈕。** 這是質詢過程一度成立的結論,論據有二。一是**棘輪不對稱**:按鈕的頁數上限是「使用者覺得值得的次數」,自動載入的上限是「壓著 PageDown 多久」,而 loaded commit window 會跨面板重載保存、沒有任何入口縮得回來。二是**所有權真空**:從未被本專案宣告、要求或使用過,零依賴,拿掉的成本最低。第二條在維護者明確要求這個功能的那一刻就不成立了。第一條成立,但它指向的是把棘輪修好,不是把功能刪掉 —— 棘輪對按鈕路徑一樣存在,刪掉自動載入並不能消除它,只能讓它慢一點咬人。

**留著程式碼,標為實驗性 / 未支援。** 三個選項裡最差:保留全部缺陷,再加一筆文件債。ADR-0014 那句「多一個設定換來的只是迴避一次判斷」對它的效力最強。

**用成本反對它** —— 每次自動觸發都要重跑 `git log` 並重建整張表,成本隨已載入筆數線性上升。否決是因為它**證明太多**:按鈕路徑付的是一模一樣的成本。一個同時反對按鈕的論證,不是能停下來的論證。

**還原時把 loaded commit window 夾回開場筆數**,把撐大的視窗當成不該保存的工作階段狀態。否決:面板每次重新變得可見都會重設 `webview.html`,亦即一次完整的重開機加狀態還原。夾在還原點上,等於「切到別的分頁看一眼再切回來,載入量歸零」—— 那不是修好,是換一個觸發頻率高得多的病。正確的方向是讓那個數字**看得見**並給明確的重設入口,而不是偷偷清掉。

**把 `requestLoadCommits` 改成排隊**,讓被丟棄的請求在前一趟結束後補送。否決:它把「至多一個載入在飛」這個目前恆真的不變量,變成「零或一個在飛 + 一個待辦」,而委派動作的排程正是靠那個單一事實在判斷現在能不能跑。加一層佇列就要同步改那條不相干的路。改成回傳 boolean 並在每個呼叫端把守衛前置,買到同一份安全而不動不變量 —— 但**「前置到哪裡」不是「函式的開頭」,是「與狀態變更同一段同步執行的最前面」**。兩者之間不得隔著任何一次等待:對話框、`setTimeout`、`await`,或任何存起來、之後由別的事件觸發的 callback。隔著等待的守衛只證明「按下去的那一刻沒有載入在飛」,而變更發生在使用者答覆之後,那時的事實可能已經相反。變更被推遲進 callback 時,守衛要跟著推遲 —— 在那段延後的程式最前面**重取**一次。

**為捲動門檻抽一個純函式**,好讓它在測試裡可驗。否決:逐 suite 用 `Object.defineProperty` stub window 幾何在本專案已有先例,~~不需要進共用的測試 setup,~~ 也不需要為此在產品程式碼上開一個 seam。

**中間那半句已失效。** 逐 suite 的先例確實存在,但它涵蓋不到沒有自備 stub 的那些 suite —— 而 jsdom 的 `document.body.offsetHeight` 恆為 0,使門檻式在那些 suite 裡**恆真**。也就是說,先例保護的是寫過它的人,沒寫的人拿到的是一個永遠成立的判斷。幾何值後來被提進共用的測試 setup,讓門檻在每一個 suite 裡都有意義。

**被否決的主張本身沒有變**:產品程式碼仍然不為這個門檻開 seam。死掉的只是「共用 setup 不必動」這半句 —— 而它與另外兩半句並列在同一句裡,容易被整句讀成仍然生效。

## 後果

- **把 CDV 捲進視野是「開啟」的一部分,不是「畫」的一部分。** 拿掉 `hideCommitDetails()` 之後,留下來的面板讓每一次重繪都重跑一次 auto-centre 捲動 —— 同一類跳動換條路回來。修法是記住已經捲進視野的那個 CDV 身分,身分沒變就不捲。**這連帶改變了 soft refresh 的既有行為**:背景重新整理不再把使用者拉回展開的那個 commit。那是同一個誤用的另一個實例,而使用者一樣沒有要求過。
- **捲動位置在這裡不是可用的工具。** 記下 `scrollY` 再還原,對移除列造成的位移無效(瀏覽器本來就停在那);而在自動路徑上,它記的是門檻觸發那一刻的位置,回應落地時會把還在往下捲的使用者往回拽 —— 從一個跳動換成另一個。兩種情形都指向同一個結論:治因,不要補償。
- **~~自動路徑與按鈕路徑不再共用全部副作用。~~ 這句標題從寫下的那天起就是錯的,而它底下那句是對的。** `hideCommitDetails()` 從兩條路徑都拿掉 —— 它在 load-more 上本來就是多餘的:載入嚴格追加,展開的 commit 不可能消失,而重繪路徑已經能重新 bind,並在真的找不到時自行清掉展開狀態。
  **從兩條路都拿掉一件事,不是分岔,恰恰是兩條路繼續共用全部副作用。** 標題與它自己的內文互相打臉,而在 #137 之前,兩條路確實一件副作用都沒有分開過。原句逐字保留並劃掉,因為讀到這裡的人會需要知道它曾經被當成先例引用過(`loadMoreCommits` 的註解與 `loadMoreOnScroll` 的 suite 都引用過,兩處已一併更正)。

  **第一次真正的分岔是「拒絕怎麼講」,而不是「做不做」。** #137 讓被拒絕的**按鈕**出聲(`dialog.loadMoreBusy`):使用者要了下一頁,要不到就是他該知道的事,而沉默的拒絕與壞掉的按鈕無從區別(`confirmForRepoAndHead`)。捲動那條**必須維持沉默** —— 它什麼都沒要求,從捲動彈錯誤框正是本篇標題禁止的那種操作級副作用。這條路上它還會反咬:對話框開著時本 listener 是關的(#124),所以多載入一頁的代價會是**之後每一頁都不再載入**,直到使用者把框關掉。
  兩條路因此由 `LoadMoreTrigger` 分開,而不是由一個 boolean 分開。**它的兩個值逐字就是本節這兩個字 —— `"operation"` 與 `"browsing"`,不是 `"press"` 與 `"scroll"`。** 用輸入裝置命名會讓下一個呼叫端問錯問題(「我這算按下去嗎」),而該問的是「使用者要求了嗎」;答案決定他欠不欠對方一句話,而那才是這兩條路唯一不共用的東西。

  **出聲那半邊有代價,而付它的是另外兩張票 —— 兩張,不是一張。** 實測過,不是推論:確認框立著、背景有 refresh 的載入在飛,把焦點移到頁尾那顆「載入更多」按下去,畫面上剩 `dialogLoadMoreBusy`,而 `#dialogAction` 不見了 —— 使用者讀到一半的那個問題連同它的 action listener 一起沒了,`dialogDismissAction` 也是被覆寫而非被執行。
  這件事的兩半各有其主,不該併成一句:**#141 是「為什麼他到得了那裡」** —— `showDialog` 沒有任何焦點圍堵,所以背景每個控制項在 overlay 後面都還 Tab 得到、按得下去;**#127 是「為什麼到了就毀掉那個問題」** —— `showDialog` 覆寫 `#dialog` 時沒有「已經有框開著」的守衛,而那正是該票已經在追的同一種覆寫衛生(它記的是被留在原地高亮的 `dialogMenuSource`)。
  **為了避開它而改回沉默不是答案** —— 那正是 #137 要拔掉的缺陷,而且會剛好只留在使用者最看不出發生什麼事的那個位置。兩帖藥都不是在這個守衛裡多加一項判斷。

- **焦點必須跨重繪存活 —— 每一個鍵盤群組都要。** 重繪前記下持有焦點的東西的身分,重繪後找回同一個身分。圖形的列用 commit hash;Commit Details View 的檔案清單用檔案路徑(索引不行,同一個檔案在 Tree 與 List 兩種版面的列號不同);頁尾的兩個控制項用它們的 id,而且身分要撐過**兩次**重繪 —— 按下載入更多時按鈕先被 spinner 換掉,頁面回來才復原,中間那一段沒有它。這是為自動載入新增的狀態,理由就是 ADR-0014:純瀏覽不得移動焦點。
  **本條原本只立法到圖形的列**,而檔案清單當時撐不過重繪 —— 焦點掉到 body,下一次方向鍵就把使用者丟進圖形,離開他原本在瀏覽的清單。兩個群組是同一條規矩的兩個實例,一個補上另一個沒補,只會讓下一個群組再重蹈一次。
  **然後它就重蹈了。** 上面那句寫下之後,頁尾的兩個控制項成了第三個群組,而它們當時連 Tab 都到不了,遑論撐過重繪 —— 補進來的時候,這一條又是被**事後**擴寫的。所以規矩的正確讀法不是「列與檔案清單」,是**任何使用者能用鍵盤停在上面的東西**;新增這種東西時,這一條就適用,不必等它先失效一次。還原一律不捲動(`focusInPlace`):重繪不是一次焦點移動,而且捲動會餵回 scroll 事件。
- **載入中觸發的自動載入整個不發生,而不是部分發生。** 守衛前置到任何狀態變更之前 —— 而且中間不得有等待;變更被推遲進 callback 時,守衛要跟著推遲。舊實作先把視窗撐大、關掉 CDV、存檔,才發現請求送不出去,於是視窗永久卡在一個從未載入的數字上,而載入更多從此完全失效。同一個陷阱在變更 commit 排序那條路上更嚴重:偏好已經存進 repo state、視窗已經縮回,圖形卻從未重載。

  「中間不得有等待」這半句是後來補的,而補它的是一個反例:`loadFindMatch` 曾經被**當成正確寫法的範本**引用進這篇 ADR 的普查,而它只在不需要確認的那條路上是對的。需要確認時,真正動狀態的程式在使用者答覆對話框**之後**才跑,中間整個時間窗裡背景重新整理都可能起一次載入。所以那次普查數到的「每個呼叫端都守好了」是假的 —— 它數的是守衛在不在,不是守衛在不在**該在的位置**。

- **loaded commit window 必須看得見,而且縮得回來 —— 對每一種輸入方式。** 這是保留自動載入的條件之一,不是可選的後續工作:自動載入把「撐大」的成本從「按 27 次」降到「壓著 PageDown」,可見性與重設入口就是它的配套。
  **末三個字是後來補的,而補它的是一次失效。** 重設入口確實做出來了,但它和「載入更多」一樣是個沒有 `tabindex` 的 `div` —— 於是這個條件有一整段時間**只對滑鼠使用者成立**,而條件的文字讀不出這件事。兩者現在是真的 `<button>`,焦點也撐得過重繪。
  這裡的教訓不在按鈕:**一個條件若沒有指明它對誰成立,它就會對寫它的人成立。** 後續要為這個功能加任何配套時,先問「用鍵盤的人拿得到嗎」。
  **然後它又失效了一次,這次不在入口,在時機。** 模態對話框開著的時候,`#dialogBacking` 是一張蓋住整個畫面的 overlay,而頁尾 —— 計數與重設入口兩者所在之處 —— 就在它底下。overlay 本身不可捲動,滾輪於是 chain 到 document,`scroll` 照發,自動載入照跑:視窗在使用者背後被撐大,而看得見與縮得回來兩半同時不成立。所以這個條件要問的不只是「誰拿得到」,還有「這一刻拿不拿得到」—— 一個平時看得見的東西,被蓋住的期間就不算看得見。

  **而修法本身又踩了上面那句話一次,所以這一條到今天仍然只補了一半。** #124 關掉的是滾輪:捲動不再在對話框開著時載入。但 `showDialog` 只設兩個 class name 與 `innerHTML` —— 背景沒有 `inert`,沒有 focus trap —— 而頁尾的「載入更多」自 #88 起是個有 tabindex 的真 `<button>`。於是 Tab 仍然走得到它,Space 仍然原生觸發它,而 keydown 的對話框分支是 `return` 而非 `preventDefault`,擋不住一個它根本沒看到的 activation。**用鍵盤的人現在照樣能在對話框後面把視窗撐大,而且一樣看不見。** 實測過,不是推論。

  這就是本條自己那句教訓的第三次應驗,而這次寫下它的人正是讀著它動手的:**一個條件若沒有指明它對誰成立,它就會對寫它的人成立** —— #124 的閘門與當時的註解,都是照著滑鼠使用者的那條路寫的。

  **所以「對每一種輸入方式」這一條,到今天仍然沒有被滿足,而滿足它的是 #141,不是 #124。** #124 關掉的是兩扇門裡的一扇(滾輪)。另一扇是 `showDialog` 完全沒有焦點圍堵 —— 沒有 `inert`、沒有 focus trap、也不移動焦點 —— 所以對話框對鍵盤根本不是模態的,**背景每一個控制項都還 Tab 得到、按得下去**;「載入更多」只是其中剛好會撐大 loaded commit window 的那一個,不是問題的大小。這也是為什麼它不該被寫成「載入更多按鈕還按得到」:那是症狀,#141 治的是病。**在 #141 落地之前,本條對鍵盤使用者不成立**,而自動載入是靠本條才留下來的 —— 這一句留在這裡,是為了不讓下一個人把 #124 讀成句點。

  **「縮得回來」那半邊現在也會講話了(#137)。** 重設入口是這個條件唯一的實作,而它在載入中被按下時原本什麼都不做 —— 條件的文字看起來成立,實際上那一刻不成立,而使用者沒有任何辦法知道自己碰到的是哪一種。`dialog.resetWindowBusy` 補的就是這個:入口存在、這一刻不能用、等一下再按同一個地方。這不是新的條件,是同一個條件終於**說得出**自己何時暫時不成立。

- **~~這個決定有到期條件。~~ 這一條已失效,見 ADR-0020。** 它的三個前提全錯:棘輪與怎麼取來無關(它講的是視窗只增不減);「webview 只追加 DOM」不是工程難度問題,是版面演算法不允許;而「重抓很貴」量測後不成立(走訪 20,800 筆的邊際成本是 55 ms,`--skip` 省 2.4 ms)。原句逐字保留於下,因為它記錄的是當時我們相信什麼 —— 刪掉它,下一個人會從零把同一個錯誤信念再推導一次:

  > **這個決定有到期條件。** 後端載入 commit 的介面是「給我前 N 筆」,所以每一頁都是重抓加全表重建。若它日後長出 append / offset 介面(給我第 N 筆之後的 M 筆,webview 只追加 DOM),棘輪與重繪兩個顧慮同時消失,自動載入就從「需要配套才成立」變成便宜的功能,上面的條件可以放寬。反過來,若任何一個條件守不住,ADR-0014 的論證會重新指向刪除。

- **未做:節流,以及那個無名的門檻。** scroll handler 沒有 throttle 或 rAF,而「距離底部 250px」是一個沒有出處的魔術數字。門檻判斷被兩個便宜的布林短路擋在前面,但預設開啟之後,那個短路對多數使用者不再成立 —— ~~現在擋在 `document.body.offsetHeight` 前面的只剩「還有沒有更多可載入」~~(#124 之後是兩項,見下)。~~載完整段歷史之後它依然是零成本~~,在那之前不是。要處理就兩件一起想。

  兩件一起想過了,結論是分開處理,而且**這一條只有量測那半邊被處理掉**。那次量測改成快取,在文件可能長高時失效(`getPageHeight` / `observePageHeight`),於是強制同步版面計算的窗口從「還有得載入期間的每個 tick」縮成「還有得載入期間的每次變動一次」。失效機制本身不受那兩個布林短路保護,所以「載完整段歷史之後零成本」現在只對**讀取**成立;理由記在 `observePageHeight` 的註解裡。**節流仍然未做,而且是決定不做,理由不重寫於此** —— 見 ADR-0020「考慮過但否決的方案 → 捲動節流」。**那個無名的 250px 仍然無名,這一條沒有被關掉。**

  **「只剩一個」也已經過期了,上面那半句因此就地劃掉。** 對話框閘門(#124)同樣便宜、同樣排在量測前面,所以擋在 `document.body.offsetHeight` 前面的現在是兩項:「還有沒有更多可載入」與「有沒有對話框開著」。**兩處數字的基準要講明,否則下一個人會以為其中一個寫錯了**:整個條件式共四項,第一項是設定讀取 `loadMoreAutomatically`,原句與這裡都不把它算進來 —— 數的是「預設開啟之後仍然擋得住的那些」,而那一項在預設開啟之後對多數使用者恆真。以條件式全部項數計則是三個布林加一次量測,`getPageHeight` 的註解就是這樣數的,而它必須跟著這裡一起改。這不是那條成本論證的答案 —— 對話框閘門擋掉的是讀對話框的那段時間,不是壓著 PageDown 的那段。順序倒是要守住:任何加進這個條件式的新項,便宜的排在量測前面,不然這一條會在沒人察覺的情況下再退回去。

- **預設開啟。** 這篇 ADR 原本把預設值留給之後 —— 先讓配套出貨、有人用過再談。維護者在配套與這篇 ADR 一起送審時就決定了:既然自動載入現在守得住上面那些條件,那麼把它藏在一個沒人會找到的開關後面,只是換一種方式讓它繼續沒有主人。
  它是對所有使用者可見的變更,所以連帶要求三件事,缺一不可:設定描述不得再把預設值寫死在文案裡(那句「Default: false」已經在這次翻轉中腐爛了一次)、README 的設定表要收錄它、以及跑在真實 extension host 的預設值測試要把它釘住。一個沒有被那條測試涵蓋的預設值,就是下一次靜默分歧。
