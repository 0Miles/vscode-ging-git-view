# 捲動自動載入留下來,但它不得產生操作級的副作用

`ging-git-view.history.loadMoreOnScroll` 保留。捲動接近底部時自動載入下一頁 commit 是**瀏覽**的延續,所以它必須與瀏覽無異:不關閉展開的 Commit Details View、不弄丟鍵盤焦點的錨點、不讓畫面在使用者眼前跳動。它撐大的 **loaded commit window** 必須看得見,而且有路縮得回來。守不住這幾件事的自動載入,不該存在。

這段程式碼自 webview UI 引進(`7824be6`)以來一個字沒改過,從未被測試涵蓋,也從未出現在 CHANGELOG 或 README。這篇 ADR 是它第一次被真正決定。

## 為什麼未來的讀者會困惑

**「自動載入不就是把按鈕自動按一下嗎?」** 不是,而這正是舊實作錯在哪裡。按鈕被按下是一個**操作**:使用者換了工作焦點,順手關掉展開的細節、把焦點交還給重繪後的表格,都還說得過去。捲到底則是**瀏覽**:使用者什麼都沒要求。兩者共用同一個函式,就等於讓瀏覽長出操作的副作用 —— ADR-0014 花了整節論證的「捲動是瀏覽,方向鍵是操作」,在這裡被反過來破壞了。

**與 ADR-0014 的張力是這篇 ADR 的主題,不是它的副作用。** 鏈條是:方向鍵移動焦點會呼叫 `scrollIntoView`,那本身就發出 scroll 事件 → 門檻成立 → 自動載入 → 整表重繪,持有焦點的列被銷毀 → `focusedRowIndex` 找不到 activeElement,退回它的 fallback 錨點,也就是展開中那一列 → 而那個錨點剛剛被同一條路徑上的 `hideCommitDetails()` 清成 null → 回傳 −1 → 下一次方向鍵從第一列開始。**使用者用方向鍵走到第 300 列,自動載入觸發,再按一次下鍵,人在第 1 列。** 所以焦點錨定不是加分項,是這個功能能否存在的前提。

**畫面跳動的來源不是重繪,是 `hideCommitDetails()`。** 在真實 Chromium 量過:整表 `innerHTML` 抽換本身**保得住**捲動位置 —— 內容只往下長,既有偏移量仍然有效,同一列停在同一個像素(量到位移 0px)。但若展開的 CDV 位於視窗上方而重繪時被移除,`scrollY` 不變、內容卻往上跑了整整一個 CDV 的高度(量到 253px,約 10 列)。所以「載入前記下 `scrollY`、載入後還原」對這個跳動**完全無效**:瀏覽器本來就停在那個位置,還原等於原地踏步。唯一有效的修法是不要移除那一列。這個跳動是 inline 模式獨有 —— docked 的 CDV 是 `position: fixed`,不在文件流內。

## 考慮過但否決的方案

**整個刪掉,只留按鈕。** 這是質詢過程一度成立的結論,論據有二。一是**棘輪不對稱**:按鈕的頁數上限是「使用者覺得值得的次數」,自動載入的上限是「壓著 PageDown 多久」,而 loaded commit window 會跨面板重載保存、沒有任何入口縮得回來。二是**所有權真空**:從未被本專案宣告、要求或使用過,零依賴,拿掉的成本最低。第二條在維護者明確要求這個功能的那一刻就不成立了。第一條成立,但它指向的是把棘輪修好,不是把功能刪掉 —— 棘輪對按鈕路徑一樣存在,刪掉自動載入並不能消除它,只能讓它慢一點咬人。

**留著程式碼,標為實驗性 / 未支援。** 三個選項裡最差:保留全部缺陷,再加一筆文件債。ADR-0014 那句「多一個設定換來的只是迴避一次判斷」對它的效力最強。

**用成本反對它** —— 每次自動觸發都要重跑 `git log` 並重建整張表,成本隨已載入筆數線性上升。否決是因為它**證明太多**:按鈕路徑付的是一模一樣的成本。一個同時反對按鈕的論證,不是能停下來的論證。

**還原時把 loaded commit window 夾回開場筆數**,把撐大的視窗當成不該保存的工作階段狀態。否決:面板每次重新變得可見都會重設 `webview.html`,亦即一次完整的重開機加狀態還原。夾在還原點上,等於「切到別的分頁看一眼再切回來,載入量歸零」—— 那不是修好,是換一個觸發頻率高得多的病。正確的方向是讓那個數字**看得見**並給明確的重設入口,而不是偷偷清掉。

**把 `requestLoadCommits` 改成排隊**,讓被丟棄的請求在前一趟結束後補送。否決:它把「至多一個載入在飛」這個目前恆真的不變量,變成「零或一個在飛 + 一個待辦」,而委派動作的排程正是靠那個單一事實在判斷現在能不能跑。加一層佇列就要同步改那條不相干的路。改成回傳 boolean 並在每個呼叫端把守衛前置,買到同一份安全而不動不變量。

**為捲動門檻抽一個純函式**,好讓它在測試裡可驗。否決:逐 suite 用 `Object.defineProperty` stub window 幾何在本專案已有先例,不需要進共用的測試 setup,也不需要為此在產品程式碼上開一個 seam。

## 後果

- **把 CDV 捲進視野是「開啟」的一部分,不是「畫」的一部分。** 拿掉 `hideCommitDetails()` 之後,留下來的面板讓每一次重繪都重跑一次 auto-centre 捲動 —— 同一類跳動換條路回來。修法是記住已經捲進視野的那個 CDV 身分,身分沒變就不捲。**這連帶改變了 soft refresh 的既有行為**:背景重新整理不再把使用者拉回展開的那個 commit。那是同一個誤用的另一個實例,而使用者一樣沒有要求過。
- **捲動位置在這裡不是可用的工具。** 記下 `scrollY` 再還原,對移除列造成的位移無效(瀏覽器本來就停在那);而在自動路徑上,它記的是門檻觸發那一刻的位置,回應落地時會把還在往下捲的使用者往回拽 —— 從一個跳動換成另一個。兩種情形都指向同一個結論:治因,不要補償。
- **自動路徑與按鈕路徑不再共用全部副作用。** `hideCommitDetails()` 從兩條路徑都拿掉 —— 它在 load-more 上本來就是多餘的:載入嚴格追加,展開的 commit 不可能消失,而重繪路徑已經能重新 bind,並在真的找不到時自行清掉展開狀態。
- **焦點必須跨重繪存活。** 重繪前記下持有焦點那一列的 commit hash,重繪後找回同一個 hash 的列。這是為自動載入新增的狀態,理由就是 ADR-0014:純瀏覽不得移動焦點。
- **載入中觸發的自動載入整個不發生,而不是部分發生。** 守衛前置到任何狀態變更之前。舊實作先把視窗撐大、關掉 CDV、存檔,才發現請求送不出去,於是視窗永久卡在一個從未載入的數字上,而載入更多從此完全失效。同一個陷阱在變更 commit 排序那條路上更嚴重:偏好已經存進 repo state、視窗已經縮回,圖形卻從未重載。
- **loaded commit window 必須看得見,而且縮得回來。** 這是保留自動載入的條件之一,不是可選的後續工作:自動載入把「撐大」的成本從「按 27 次」降到「壓著 PageDown」,可見性與重設入口就是它的配套。
- **這個決定有到期條件。** 後端載入 commit 的介面是「給我前 N 筆」,所以每一頁都是重抓加全表重建。若它日後長出 append / offset 介面(給我第 N 筆之後的 M 筆,webview 只追加 DOM),棘輪與重繪兩個顧慮同時消失,自動載入就從「需要配套才成立」變成便宜的功能,上面的條件可以放寬。反過來,若任何一個條件守不住,ADR-0014 的論證會重新指向刪除。
- **未做:節流,以及那個無名的門檻。** scroll handler 沒有 throttle 或 rAF,而「距離底部 250px」是一個沒有出處的魔術數字。門檻判斷被兩個便宜的布林短路擋在前面,但預設開啟之後,那個短路對多數使用者不再成立 —— 現在擋在 `document.body.offsetHeight` 前面的只剩「還有沒有更多可載入」。載完整段歷史之後它依然是零成本,在那之前不是。要處理就兩件一起想。
- **預設開啟。** 這篇 ADR 原本把預設值留給之後 —— 先讓配套出貨、有人用過再談。維護者在配套與這篇 ADR 一起送審時就決定了:既然自動載入現在守得住上面那些條件,那麼把它藏在一個沒人會找到的開關後面,只是換一種方式讓它繼續沒有主人。
  它是對所有使用者可見的變更,所以連帶要求三件事,缺一不可:設定描述不得再把預設值寫死在文案裡(那句「Default: false」已經在這次翻轉中腐爛了一次)、README 的設定表要收錄它、以及跑在真實 extension host 的預設值測試要把它釘住。一個沒有被那條測試涵蓋的預設值,就是下一次靜默分歧。
