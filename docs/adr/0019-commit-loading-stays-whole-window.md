# 後端不長 append / offset 介面,載入仍然是整個視窗

commit 載入維持現狀:每次都向後端要「前 N 筆」,回來重建整張表與整個圖形版面。ADR-0018 把「後端長出 append / offset 介面」寫成它的到期條件,那條到期條件**三個前提全錯**,已在該處原地標記失效。

這篇 ADR 記錄的是一個**不做**的決定,以及它為什麼值得佔一個編號:提案本身聽起來理所當然(「別每次都重抓」),而推翻它需要的證據不是讀程式碼讀得出來的。下一個人會再想到同一件事,他該撞到的是數字。

## 為什麼未來的讀者會困惑

**「重抓整份不是很浪費嗎?」** 量過了,不浪費 —— 因為那不是成本所在。在一個 20,800 個 commit、401 個 ref 的存放庫上(Windows,合成歷史:主線加每 50 筆一次 side branch 與 merge back):

| 呼叫                                  | 時間     |
| ------------------------------------- | -------- |
| `git --version`(純行程啟動)           | 91.7 ms  |
| `git log --max-count=301`             | 237.2 ms |
| `git log --max-count=1001`            | 237.0 ms |
| `git log --max-count=3001`            | 243.9 ms |
| `git log --max-count=20801`(全部)     | 291.6 ms |
| `git log --skip=300 --max-count=101`  | 234.6 ms |
| `git log --skip=2900 --max-count=101` | 237.1 ms |
| `git show-ref -d --head`(401 refs)    | 178.3 ms |

開存放庫加解析 ref 的固定成本是 **~145 ms**;走訪 300 筆的邊際成本趨近於零,走訪**全部 20,800 筆**是 55 ms。`--skip` 對比 `--max-count` 省下 **2.4 ms —— 在雜訊裡**。而 `getRefs` 與載入筆數無關,它與 `git log` 在同一個 `Promise.all` 裡並行,所以那 178 ms 一直被遮著 —— append 不會讓任何一支縮短到會露出另一支的程度。

webview 那一側(真實 Chromium):3000 列的字串組裝加 `innerHTML` 加逐元素綁定合計 **41 ms**,其中把逐元素綁定換成事件委派只省 **3.5 ms**。

**append 針對的是佔比約 1% 的項,而且只能省下那 1% 的一部分。**

**「那為什麼不順手做?反正很便宜。」** 因為它在原廠設定下**一次都不會跑**。stash 不是 `git log` 的輸出,它是依日期被 splice 進 commit 清單的,所以第 0 頁的 stash 位置本身就是「載了多少」的函數 —— 分頁契約要成立,開著 stash 就得退回整份重抓。而 `show.stashes` 與 `show.uncommittedChanges` 的宣告預設都是 `true`,而且整份 manifest 只有 `defaultFileEncoding` 宣告了 `"scope": "resource"`,所以兩者**不能依存放庫覆寫**。兩件事相乘,append 只服務那些主動關掉 stash 的使用者。

這條推論**不需要任何量測**,所以它是這個決定的主要理由;量測是次要的,因為量測依賴平台、拓撲與快取狀態,而這條只依賴 manifest 裡的兩個 `default`。

**「ADR-0018 說 webview 可以只追加 DOM。」** 那半句是錯的,而且不是工程難度問題 —— **是版面演算法不允許**。

`graph.ts` 在只載第一頁時,把**所有**落在圖外的 parent 摺成同一個 id 為 -1 的 sentinel vertex。而 merge 的處理有兩條路。走 merge 那一支需要「這個 parent 當下已經掛在某條 branch 上」,而 sentinel 永遠不在 vertex 陣列裡、永遠沒被指派到 branch,所以第一頁一律走「配一條新 branch」那一支 —— 配新顏色、把線一路畫到下緣、下方每一列各吃掉一個 lane。第二頁讓那個 parent 變成真的 vertex **且它當下已經掛在某條 branch 上**時,同一個 merge 改走 merge 那一支,併進既有接點後提早收尾:不再吃 lane、不再配顏色,於是之後每一次顏色配置的結果整串位移。

所以**既有列的繪製會隨載入集合變大而改變,而這是今天就有的行為** —— 每次全清重建正是它的成因。「保證上方不變」不是現行程式碼具備的性質,append 不是要保住它,是要決定要不要第一次去造它。

那個判斷式裡另外還寫著一句明示的 sentinel 檢查(`parentVertex.getId() > -1`),但它是**多餘的** —— 實測拿掉它,版面數值一個字都不變,因為「已經掛在某條 branch 上」那一句已經把 sentinel 擋掉了。會找錯行的人請看這裡。

最小重現(已由兩個獨立實作交叉驗證,並固定在 `tests/webview/graphLayout.test.ts`):第一頁三列 —— `M` 的 parents 是 `[A, P]`、`A` 的 parent 是 `P`、`Z` 的 parent 也是 `P`;`P` 落在第二頁。第二頁到達後 `Z` 的 lane 寬度由 62 變成 46、顏色由 2 變成 1。

發生率(6000 個合成存放庫,修正後的產生器):既有列繪製改變 **10.1%**,vertex 真的換 lane 或換色 **2.8%**。移除「合併後分支繼續長 commit」這個 motif 之後降為 **0.0%**。

**翻轉是必要但不充分。** 12,000 例中,「沒有發生那個翻轉卻改變了繪製」**零次**;「翻轉了但視覺上什麼都沒變」**389 次**。所以測試**不得**斷言「翻轉 ⇒ 一定看得見變化」,那樣寫會 flaky。

## 考慮過但否決的方案

**只把 append 用在傳輸層** —— 後端少抓、IPC 少傳,webview 仍然全量重算版面、全量重建表格,視覺與今天逐像素相同。這是唯一在正確性上站得住的 append 形態,而它被上面兩條理由否決:原廠設定下不觸發,而且省下的量在雜訊裡。它的代價則是具體的:載入 payload 要同時服務「視窗」與「頁」兩種語意、後端那支查詢要同時服務兩種語意、兩套 stash 與 uncommitted 行為、兩個「還有沒有更多」的推導,外加防止頁與頁重疊的封印與去重守衛。**用一份雙路徑介面的永久維護成本,換 2.4 ms。**

**凍結第一頁版面,只替新列排版。** 這是唯一能讓「只追加 DOM」成真的形態,而它賣掉的是一個今天成立、而且最好推理的性質:**版面是已載入清單的純函數**。賣掉之後版面變成路徑相依 —— 一次載 500 筆與分五次載 100 筆畫出來不一樣。而它的觸發點是必然而非邊角:面板重載時會把整份存下來的清單**一次**餵進去,而面板每次重新變得可見就是一次完整重開機加狀態還原。所以在這個方案下,「分五次載到 500 筆 → 切到別的分頁看一眼 → 切回來 → 同一份歷史畫出不同的圖」。使用者無法把它歸因到任何動作上。

**保留提案、標為未來方向。** 一條錯的、仍然看起來生效的批准,比沒有批准更危險 —— 它會被當成「維護者已經批准過的方向」拿出來用。ADR-0018 的那條到期條件就是這樣一張許可證,所以它被原地標記失效,而不是留著等人引用。

**改 `show.stashes` 的預設值,好讓 append 有機會觸發。** 為了讓一個效能改動能夠執行而更動使用者可見的預設,是本末倒置。

**寫一條「版面是載入清單的純函數」的性質測試。** 它在今天的程式碼上**不可能失敗** —— 版面建構的第一件事就是把 vertices、branches、顏色配置整個清空,純函數性是建構上的而非碰巧的。一個不可能紅的測試守的不是程式碼,是一個決定;而決定該寫在這裡,不是偽裝成測試。

**捲動節流。** 一次成功載入長出約 100 列(約 2400 px),而觸發門檻是距底 250 px —— 每次載入都把底部推離門檻近十倍距離,所以連續觸發在結構上到不了。真正存在的成本是每個捲動 tick 一次的強制同步版面計算,那與節流是兩件事,見後果。

## 後果

- **ADR-0018 的到期條件失效,但那篇 ADR 的決定沒有。** `0018` 的主張是「自動載入留下來,但不得產生操作級副作用」,它一個字都沒有被推翻;死掉的只是「後果」清單裡的一條。因此 `0018` 的 `status` 維持 `accepted`,只在那一條原地標記 supersede。整篇改狀態會連帶把三張已交付的票(不再關閉 Commit Details View、焦點跨重繪存活、載入視窗看得見縮得回來)的存在理由打上問號,而那三個機制在這個決定之下理由完全不變 —— 重繪照舊、焦點照舊會被銷毀、棘輪照舊只增不減。
- **`loadMoreOnScroll` 的預設值維持 `true`。** 翻預設的依據是「自動載入現在守得住那些條件」,指的是上述三項配套,不是這條到期條件。配套一項未動。
- **「棘輪與重繪兩個顧慮同時消失」兌現的是四分之一。** 棘輪講的是載入視窗只增不減、跨面板重載存活,與怎麼取來無關;append 就算做了也動不到它。
- **`--skip` 這個選項留下一個已知的坑,記在這裡免得下次重踩:** 它是走完再丟,不是跳躍,所以第 N 頁的後端成本仍是 O(skip+count);而且它是位置式的,兩次呼叫之間只要有人 commit、fetch 或切分支,同一個 `--skip` 指到的就不是同一筆,結果是頁與頁重疊或破洞。commit 查詢的 scope 是多 tip 的,`git log` 對這種遍歷**沒有續傳 token**,所以 cursor 在這裡不是脆而是不可表達。
- **未做,而且與這個決定脫鉤:webview 在大視窗下到底慢在哪,仍然沒有答案。** 這次量測翻出四個沒有人看過的候選,而固定成本 ~237 ms 裡 `git log` 的邊際只有 6.7 ms,所以瓶頸不在後端。版面走訪在 6000 列量到 89 ms 且**超線性**(3000 列是 12.5 ms,列數兩倍而時間七倍),但那是在 Node 而非真正的 webview 引擎上量的,而且那個超線性至少有三個成因候選、三者修法完全不同 —— 在歸因之前不該動它。另外三個候選完全沒量過:把整份 commit 清單序列化進面板狀態(呼叫點遍佈高頻路徑)、圖形 SVG 每次重繪都重建全部節點、以及背景重新整理時對整份清單做的深度比對。
