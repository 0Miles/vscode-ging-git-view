# 清理對話框是批次動作的第二個來源,不經樹選取

清理 cleanup candidate 的對話框自己收集逐列勾選,確認後**直接**送出 `runRefBatchAction`,不透過分支側檢視的多選。批次刪除的**執行**仍然只有一套(`deleteBranches` 請求、force 回合、摘要);分岔的只是入口的那個詢問。

## 為什麼未來的讀者會困惑

ADR-0008 立的規矩是「側檢視的選取集同時是圖形篩選器與批次動作的目標」,ADR-0009 的後果段又明寫「issue #12 的待決問題要照這條 ADR 重新回答」。讀者會合理預期清理功能就是「幫使用者把候選選起來,再讓他右鍵批次刪除」—— 那也正是 issue #12 留言裡的設想。結果程式碼裡有**兩個**批次來源,看起來像是有人繞過了既有設計。

繞不開的是一個 API 事實:**`TreeView` 沒有任何辦法程式化地做出多選**。`TreeView.selection` 是唯讀,`reveal` 一次只選一個(見 `src/extension/branchesView.ts` 的模組註解與 `searchBranch` 註解)。既有的多選搜尋就是為此繞路的 —— 它不去選樹,而是直接寫 branch filter 再把視覺選取清掉。而批次刪除的 target 來自 VS Code 傳進來的 tree selection,不是 filter。所以「把候選選起來讓使用者右鍵刪除」這條路在現有 API 下**根本走不通**:寫了 filter,圖形會只剩候選,但右鍵選單連 `listMultiSelection` 都不會成立。

`runRefBatchAction` 訊息帶的本來就是明確的 `targets: string[]`,接縫已經在了。用它就是承認來源不只一個,而不是假裝選取能被程式化寫入。

## 考慮過但否決的方案

**只寫 branch filter,要使用者自己在樹上再多選一次。** 照抄多選搜尋那條路,不需要新的來源。否決原因是它沒有解決任何事:使用者得做兩次選擇,而 issue #12 要消滅的正是「一條一條自己挑」。

**用 `TreeItem.checkboxState` 讓選取真的可以程式化設定。** ADR-0008 已經為此否決過(視覺語彙與 merged 徽章的 `✓` 打架,`showAll` / search QuickPick / 跨 repo 切換三處既有互動的規則全部翻倍)。這張票不足以推翻它。

**候選清單用原生 QuickPick,確認後再交給既有的批次刪除確認框。** issue #12 留言的設想。否決原因有二:一是**雙重確認** —— 使用者剛勾完一批分支,圖形面板跳到前景,又一個確認框逐條列出同一批問他確不確定;二是深度檢查要顯示進度、要能取消、掃完要讓清單長出新列,而 `showQuickPick` 重建 items 時已勾好的狀態得自己想辦法保住。

## 後果

- **只有一個對話框,沒有第二次確認。** 逐列 checkbox + 深度檢查鈕 + 既有的「強制刪除」「同時刪除遠端」選項長在同一個 webview 對話框裡,確認後直接進 batch run。它與既有的批次刪除確認框是**兩個不同的詢問**(一個逐列可勾、一個固定清單),背後同一條 batch run —— 符合 ADR-0009 的分界:要詢問的就長在 webview。
- **深度檢查掃的是「尚未判定為 merged 的全部分支」,不是清單上已列出的那些。** 讀者會看到它掃了畫面上沒顯示的分支,那是刻意的:昨天剛 squash merge 的分支既不 merged(ancestry 不成立)也不 inactive(commit 很新),不掃全部就永遠進不了清單 —— 而它正是最該清掉的那一種。掃描結果會讓清單**長出新列**,不只是替既有的列加標記。merged 的那些不掃,`CONTEXT.md` 已寫明每個 merged branch 都是 redundant branch,答案已知。
- **圖形會收到 inactive 集合,但沒有任何東西畫它。** 右鍵入口的出現條件是「該分支是 cleanup candidate」,兩個介面共用同一條規則,所以圖形也得認得 inactive。它**只**餵選單可見性:圖形照舊不淡化、不隱藏長期沒動的分支(ADR-0004 在圖形側的結論未被動到)。看到一份沒人渲染的資料時,不要當成殘留而刪掉。
- **候選集合在 extension host 算。** `branchFacts` 已經是分類事實的單一持有者(ADR-0013),豁免所需的輸入都在那裡。因此候選為空時,host 在**召喚圖形面板之前**就知道,直接出一則原生訊息 —— 不會為了說「沒東西可清」而把面板叫到前景。
- **候選的豁免自成一套,不等於 hidable。** 排除 checked-out、default branch 與其同名本地分支、`alwaysShow` 樣式;**不**排除 branch filter。理由是 ADR-0008 記過「批次刪除前,圖形剛好只顯示即將被刪的那幾條」—— filter 裡裝的常常正是要刪的東西,拿它當刪除豁免會直接打架。filter 的豁免動機是 ADR-0003 的呈現顧慮,搬到刪除上沒有理由。
- **`Action target` 的定義因此改寫**,來源一般化為兩個。清理那條路的扣除恆為空(候選豁免已先排除 checked-out,而 remote 對刪除是合法的)。
- **這個對話框只有「強制刪除」一個選項,沒有「同時刪除遠端」。** 側檢視的批次刪除需要它:那裡的選取集是本地分支,遠端沒有別的路徑可走,所以才有那套對選取集裡對應 remote 節點去重的邏輯。這裡每個遠端候選本來就是自己一列,再放一個 checkbox 就是同一批 ref 的第二條、而且看不見的刪除路徑。代價是:遠端分支若因不是候選、或因「顯示遠端分支」關閉而不在清單上,就不能從這個對話框刪 —— 那是側檢視批次刪除的工作。
- **分組標題在該組非空時一律出現,不照分支樹「兩種都有才出標題」的規則。** 樹裡孤零零一個 `Local` 是純噪音,但這裡標題承載該組的全選控制;一個沒有辦法整組全選的分組是更差的結果。標題的 checkbox 是三態的,部分勾選時呈現 indeterminate,而點它是往「全勾」走。
