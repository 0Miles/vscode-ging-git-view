# 導覽作廢在飛的載入,而不是為它讓路

**navigation(導覽)** 是改變「哪些 commit 該在畫面上」的操作:換存放庫、換分支篩選、切換遠端分支顯示、變更 commit 排序,以及隱藏/顯示個別 remote。最後那個是晚一步收進來的第五種,原本被漏在這篇之外,理由與收法都在〈後果〉;下面談「四種」的地方講的都是原本那四種。導覽**不得靜默落空** —— 圖形上的 commit 永遠屬於當下的存放庫與當下的篩選,不存在「設定改了、畫面沒跟上,而且沒有人會來收拾」這種狀態。

前三種(以及後來的第五種)靠**作廢**達成:載入進行中發生導覽時,在飛的 branch 與 commit 載入先被作廢,新的請求隨即送出;被作廢的那些答案照樣會回來(沒有人能叫停一個已經在跑的 `git log`),回來時由請求上帶的 **navigation token** 認出來並丟掉。

第四種(commit 排序)已經有另一條出路 —— 它在載入進行中**出聲拒絕**,而且守衛站在任何狀態變更之前,所以什麼都沒有改、也沒有債留下。維持現狀,理由見下。這說的是面板自己那個欄位標題選單;同一個排序若是從面板**外**抵達(另一個圖形面板、可分享的設定檔),就沒有守衛可站,走的是第五種入口那條比對路徑。

ADR-0019 的「同時至多一個 commit load 在飛」原封不動 —— 作廢是**先**發生的,新請求送出的那一刻在飛的仍然只有一個。改掉的不是幾個,是**誰讓路**。

## 為什麼未來的讀者會困惑

**「refresh 被丟棄是刻意的,為什麼導覽就不行?」** 因為兩者被丟到的地方不一樣,而這個差別決定了「有沒有人會來收拾」。

refresh 被丟棄時,它是丟到另一個**問同一個問題**的載入上 —— 唯一會發出 branch 請求的就是 refresh,而 commit 請求問的是同一個存放庫、同一組篩選。那個載入的答案會是對的,所以被丟棄的 refresh 沒有留下任何債。

導覽被丟到的載入問的是**另一個問題**:上一個存放庫的歷史、上一組篩選的 commit。它的答案永遠不會是對的,而且**沒有人會再問一次** —— 導覽只發生一次,而面板的閘門會拒絕之後每一次補救的嘗試,包括使用者自己按下的 Refresh。畫面於是停在前一個存放庫的圖形、掛著新存放庫的標題,直到分頁被關掉重開。

這正是 #84 回報的症狀,而它在 worktree 之間切換時最容易撞到:一次 worktree 切換往往就是一次面板重載(面板每次重新變得可見都會重設 `webview.html`),而重載後的開場載入正在跑,使用者卻已經在原始檔控制清單裡點下一個 worktree。第二次點擊什麼都不會發生,第三次也是。

**「作廢就夠了,為什麼還要 token?」** 因為作廢之後**立刻**就送出了新的請求,而 webview 與 host 之間的訊息是 command-keyed 而非 request-id'd:兩個 `loadCommits` 答案在空中,收件端無從分辨。沒有 token,被作廢的答案會被當成新請求的答案畫上去,而且會觸發新請求的 callback —— branch 那一半的 callback 會據此送出 commit 請求,帶著上一個存放庫的篩選。所以 token 不是保險,是作廢能夠成立的前提。

**「用存放庫比對不就好了?」** 擋得住換存放庫,擋不住另外兩種導覽 —— 切換遠端分支顯示與變更分支篩選都發生在**同一個**存放庫上,兩邊的 repo 一模一樣。token 數的是導覽,不是存放庫,所以三種一視同仁。

**「為什麼不叫後端把 git 停掉?」** 因為在今天的接線下停不掉,而且不停的代價很小。`simple-git` 確實吃 `AbortSignal`,但圖形面板用的 `gitClient` 是與**寫入操作共用**的一個可變 handle,在切換存放庫時扯掉它,等於讓一次跑到一半的 merge 或 delete 面對一個被中止的子行程 —— 為了省下一次唯讀查詢的餘熱,換來一類全新的資料風險。

這條理由**只涵蓋那個共用 handle**,說得更滿就不對了:`repoGitClients` 已經在提供短命、per-repo、與面板互不干擾的唯讀 client(`branchFacts` 每次讀取都用它),commit 查詢改走那條路的話,`AbortSignal` 就掛得上,而且那是唯一能**真的殺掉**那個白費的 `git log` 的辦法。沒有一起做,是因為代價不成比例:一次被作廢的載入白費的是最多四個 git 子行程加一趟結果搬運,而且它不會排隊擋住新的讀取(`setRepo` 重建 client,新 client 有自己的佇列),換來的卻是 commit 查詢與寫入操作分家這個不小的接線改動。**這是留著的優化,不是關著的門** —— 下一個想做取消的人該知道路是通的。

## 考慮過但否決的方案

**延後:記下「載入完成後要重新載入」,等在飛的那個回來再動。** 這是最保守的形態,也是唯一會**保留** #84 那個死結的形態。它把出路綁在「在飛的載入一定會回來」這個前提上,而使用者回報的正是它不回來的那些時候 —— 一個永遠不 resolve 的 `git` 子行程(Windows 上的防毒掃描、網路磁碟、`index.lock` 的擁有者卡住)會讓面板永遠等下去,而「關掉分頁重開」仍然是唯一的解法。修一個死結不該把新的行為建在同一個前提上。

**排隊:把被拒絕的請求排到後面。** ADR-0019 已經否決過一次,理由沒有變:delegated ref action 是拿「同時至多一個載入在飛」這個**單一事實**來排程自己的,佇列會讓那個事實變成一個需要展開才讀得懂的狀態。而且排隊解的是「兩個請求都想跑」,這裡的問題是「其中一個不該跑」。

**讓導覽等待,但顯示可取消的載入中畫面。** 多一個使用者要做的決定,換來的是他本來就會做的那個決定(他已經點了另一個 worktree,那就是答案)。ADR-0014 的「多一個設定換來的只是迴避一次判斷」在這裡同樣成立。

**把 commit 排序也改成用作廢達成。** 兩條出路都守得住「不得靜默落空」,而它已經走在另一條上:載入中選它會被出聲拒絕,守衛站在狀態變更之前,所以偏好沒被寫下、視窗沒被清掉、搜尋索引沒被丟掉,使用者再點一次就成立。改成作廢只會把一個**看得見**的拒絕換成一個看不見的重載。

分野**不是**「誰觸發的」 —— 換存放庫一樣有使用者親手按的入口(工具列的存放庫下拉、檔案樹裡點開的 sub-repo),那兩個走的也是作廢。真正的分野是**拒絕得起還是拒絕不起**:排序的守衛站在第一行,拒絕它等於什麼都沒發生;而換存放庫在送出重載之前,`currentRepo` 已經換了、`selectRepo` 已經送給 host 了,拒絕只會留下半套狀態。**新增一種導覽時要問的就是這一句**:在送出載入之前,狀態動了沒有?動了就只能作廢。

## 後果

- **busy claim 的擁有權必須被記下來,不能從「有沒有 callback」推。** 作廢一個 callback 等於接手它欠的東西,而它欠多少並不一致:refresh 與分支篩選重載各欠一個 claim,Load More 與 loaded commit window 的重設**一個都不欠**(它們用頁尾的載入中那一行說話,不碰 Refresh 按鈕)。憑 callback 存在就釋放一個 claim,會扣掉別人的,指示器於是在還有載入在跑的時候熄掉。所以 `commitLoadHoldsBusyClaim` 由請求的發出者明講,像 `webviewBridge` 的 `mutatesRepo` 一樣不給預設值。
- **`reloadForBranchChange` 從「載入中就整個放棄」變成導覽。** 連帶修掉的是:篩選改了、chip 也更新了,圖形卻停在舊篩選的 commit 上。它作廢的兩半裡,branch 那一半特別值得記:它的答案帶著**變更之前**host 解析出來的 filter,套用下去會把使用者剛選的選集蓋回舊的。
- **第五個入口已經收進來了:隱藏/顯示個別 remote。** `hiddenRemotes` 會變成 `git log` 的 `--exclude=<remote>/*`,所以切換它確實改變「哪些 commit 該在畫面上」;它卻只是 `sendRepos()` 加一則普通的 `refresh`,而普通的 refresh 是丟得掉的。它原本落在這篇之外,不是因為判斷過,是因為這個泛化是照著 ADR-0019 列的那四種(清掉 loaded commit window 的那些)畫的,而它不清視窗。

  認出它的方式不是再加一則訊息,而是 `loadRepos` 比對它收到的 repo state 裡那些**會餵進 `loadCommits` 請求**的欄位(`hiddenRemotes`、`commitOrdering`),變了就導覽(`commitScopeChanged`)。這樣以後每一個新的同類欄位,在被寫進那個比較的那一天就自動被涵蓋,而且 host 端不必知道自己剛做的是一次導覽 —— 它照舊寫狀態、照舊送那則丟得掉的 refresh,只是那則 refresh 現在落在導覽自己的載入上,被丟掉是對的。`showRemoteBranches` 仍然不在比較裡:它同樣左右那個查詢,但由 host 從 repo state 自己解析、從不搭上請求(ADR-0013),而且要收進來還得一併同步側檢視那個 toggle 讀的副本,那是另一個修正。

  **而這篇沒有答的那個問題,答案是不縮。** 三個理由。一,`setRepo` 之所以縮,一半是因為「你沒有同意在**這個**存放庫上付一個撐大視窗的錢」—— 新存放庫是另一段歷史,那個數字換了意思;隱藏 remote 是同一個存放庫、同一段歷史、少幾組 ref,而排除只會讓 `git log` 更便宜,那個成本論證在這裡根本不存在。二,兩種錯誤的代價不對稱:不縮而使用者想縮,是頁尾那個專為此而設的重設入口按一下;縮了而使用者不想縮,是 Load More 按 N 次。兩邊都說得通的時候,選錯誤比較好收拾的那一邊。三,這條路徑也會為**不是這個面板做的**變更而觸發 —— 可分享的設定檔隨著一次 pull 改了,或第二個圖形面板動了手 —— 在使用者沒動手的情況下把他撐大的圖形收掉,是他無從歸因的損失。

  這條決定**不**主張「`setShowRemoteBranches` 縮、而它不縮」之間有原則性的界線 —— 沒有,兩者是同一類操作的兩種粒度。它主張的是不擴散一個繼承來的副作用:ADR-0019 自己就記過,那四種是「為了別的目的而做、順帶」清掉視窗的,而那個順帶正是頁尾重設入口存在的理由。更要緊的是這個泛化的預設值 —— 規則若是「變了就導覽**並且**縮」,以後每一個被加進 `commitScopeChanged` 的欄位都自動繼承一個破壞性副作用;規則是「導覽,不縮」,泛化才安全,真的該縮的欄位再自己講。把 `setShowRemoteBranches` 改成不縮是另一個使用者看得見的行為變更,不在這篇裡。

- **仍然沒有解的:沒有導覽時,一個永不回應的載入照樣鎖住面板。** Refresh 按鈕的請求會被同一個閘門丟棄,而它不是導覽,不會作廢任何東西。要蓋掉這最後一格,需要的是一個看門狗(載入超時後把它作廢並讓使用者重試),那是另一個決定,不在這篇裡。今天的出路仍然是切換到別的存放庫再切回來 —— 而在這篇之前,連那個都沒有用。
