# 側檢視的選取集同時是圖形篩選器與批次動作的目標

分支側檢視的多選只有**一個**集合,它同時餵給兩件事:圖形要顯示哪些分支,以及右鍵批次動作要作用在哪些分支。刻意不引入第二個集合(例如 `TreeItem.checkboxState` 的勾選)把兩者拆開。

## 為什麼未來的讀者會困惑

「選幾條來看圖」和「選幾條來刪掉」是兩種心智完全不同的操作,綁在同一個手勢上,使用者為了看圖而多選之後,一右鍵就是對著 5 條分支開刀。這個風險在決策時被提出並權衡過,不是沒想到。緩解手段只有兩個:選單文案明確用複數(「刪除選取的 branch…」),以及確認框逐條列出實際會動到的分支。兩者都是緩解,不是消除。

保留單一集合的理由:checkbox 會在每一列**左側**多一個 ✓,而該列右側已經可能有一個意義完全不同的 ✓(merged 徽章),同一列上兩個 ✓ 打架;而且兩個集合意味著 `showAll`、search QuickPick、跨 repo 切換這三處既有互動全部要重新定義「動到的是哪一個集合」,規則翻倍。

## 考慮過但否決的方案

**用 `TreeItem.checkboxState` 當批次目標,反白選取繼續當篩選器。** API 確實可用(@types/vscode 1.98 起有 `checkboxState` 與 `onDidChangeCheckboxState`)。否決原因見上:視覺語彙衝突,加上三處既有互動的規則翻倍。

**反過來,checkbox 當篩選器、反白選取當批次目標。** 更糟。篩選是高頻操作,把它從單擊降級成勾選,等於為了低頻的批次動作犧牲高頻路徑。

**選 folder / group 節點時展開成底下所有 leaf。** 「刪掉整個 `feature/`」變成一個手勢,很誘人。否決原因是 group 節點(`Local` / `Remote` 兩個標題)在結構上和 folder 一樣是非 leaf,一視同仁的話**選中「Local」標題再按刪除 = 刪光全部本地分支**;要避開就得對 folder 和 group 訂兩套規則,而規則一分岔就開始漏。

## 後果

- 批次刪除前,圖形剛好只顯示即將被刪的那幾條。這是單一集合的意外好處,等於免費的預覽。
- 動作完成後不需要任何收尾程式碼:死掉的 leaf 從樹上消失,VS Code 自動把它們踢出選取集並觸發 `onDidChangeSelection`,篩選器跟著縮到倖存者;全刪光時 `pruneBranchFilter` 把它清成「顯示全部」。**不要**在動作完成後額外呼叫 `clearSelection()`。
- 之後若要補上 checkbox,對已經學會「反白 = 篩選 + 批次目標」的使用者是語意變更,不是純粹的新增功能。
