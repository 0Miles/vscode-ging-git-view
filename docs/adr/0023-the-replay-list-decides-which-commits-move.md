# 重放清單是「哪些 commit 會被搬」的唯一真相來源,指令由勾選結果選出

rebase 對話框列出這次 **git 真的會重放**的每一個 commit,每一筆都可以取消勾選;送出時跑哪一個 git 指令,由剩下的勾選決定。普通 rebase(`git rebase <obj>`)與範圍 rebase(`git rebase --onto …`)兩種對話框都是這樣,側檢視按出來的那個也是。

這取代 [ADR-0022](0022-rebase-onto-resolves-the-range-and-names-the-branch.md) 的一半:「使用者自己從手勢推導出開閉區間、看不懂就去讀那行印出來的指令」。那一條在 ADR-0022 裡已原地標記失效。**另一半一個字都沒有被推翻** —— 範圍的方向由 ancestry 判定而非點選順序、tip 送的是分支名所以被搬的是分支而不是 detached HEAD、以及對話框必須把最終要跑的那行原樣印出來(`signing.commits` 開著時 `-S` 也要在裡面)。最後那一條與本篇**互補而不是被本篇取代**:清單答的是「哪些 commit」,那一行答的是「哪一個 git 指令、哪些參數、哪條分支會被搬」。

## 為什麼未來的讀者會困惑

**一、手勢從來就表達不了半開區間,而且沒有任何工具嘗試過 —— 所以這個範圍不再是半開的。** `git rebase --onto X A B` 重放的是 `A..B` —— **不含 A、含 B**。「CTRL 選兩個 commit」這個手勢在任何介面裡都讀作「這兩個都算」,何況它是從 Commit Details View 的「比較兩個 commit」借來的,而比較是對稱的。實際使用時,使用者對範圍的兩種猜測(「兩個都搬」與「範圍含第二個」)各對一半 —— 手勢傳達不了真相。

查過的前例支持同一個結論:**沒有任何工具用「選兩個 commit」表達範圍。** lazygit 標記**單一** commit 當 base,並在畫面上把「不被包含的那一個」畫出來;GitKraken 與 Fork 用拖放,單位是整條分支;Sourcetree、GitLens 與上游 Git Graph 只有單一 commit,根本沒有範圍的概念。所以修法不是把手勢解釋得更清楚,是不要讓手勢承擔這件事:把每一筆列出來。

**二、沒有動過勾選的對話框,必須跑原本那一個指令。** 這是規格的硬條件,不是偏好 —— 對話框只是多長了一份清單,而一份沒有人碰過的清單不構成任何請求。程式碼把它做成**結構上的**而不是推導出來的:`rebasePickPlan` 在把清單交給 `planRebase` 之前先答掉「全部都勾」這一種,而未動的那條路送出的是呼叫端**原本那一則訊息**,欄位一字不差(`sendRebasePick` 收的是一個 closure,不是另一種訊息形狀)。

非這樣寫不可的理由是 `planRebase` 把**空清單**讀成「全部被取消勾選」 —— 而空清單不是那件事:一個沒有東西要重放的範圍是一次 fast-forward,git 照跑不誤。兩者若共用同一條判斷,「不勾就不會改變任何事」這句保證會在最無害的情況下破掉。

**三、「去掉最新的那幾筆」不能用 `--onto` 表達。** 它看起來只是把上界往回挪,但 `git rebase --onto X A <較早的 tip>` 會把那個較早的 tip **detach 出來** check out:分支留在原地、還指著原本那些 commit,而重放出來的是憑空多出來的第二份。使用者選一段 commit 說「搬過去」,要的是分支跟著走。interactive 那條路保住 git 的 `head-name`,分支才真的被搬。判準因此是:

| 勾選                                   | 執行                                                |
| -------------------------------------- | --------------------------------------------------- |
| 沒動                                   | 原本那一個指令,既有 action 一個欄位都不改           |
| 只去掉最舊的幾筆,**且清單是一條鏈**    | 同一次 rebase,`<upstream>` 往前挪到最後一筆被丟掉的 |
| 中間挖洞 / 去掉最新的 / 清單不是一條鏈 | `rebase --interactive` 加上我們自己寫的 todo        |
| 全不勾                                 | 不叫 git,對話框說明為什麼                           |

「同一次 rebase」不代表同一串字:普通 rebase 的 `git rebase <obj>` narrowed 之後寫成 `git rebase --onto <obj> <新下界> <branch>`,因為單一參數的形式沒有地方可以表達下界。兩者的差別見第七節 —— 量過之後只有下界與具名的分支這兩項,沒有別的。

還有一種會退回 interactive:`narrowed` 需要一個 `<branch>` 才搬得動分支,而**普通 rebase 對話框在 HEAD 已經 detached 時**給不出來(它的 tip 就是 `gitBranchHead`,那時是 null)。那時改走 interactive —— 它重放的是同一組 commit(被丟掉的那幾筆寫成 `drop`),是同一次 rebase 的另一種寫法,不是另一次 rebase。

**範圍對話框不走這條退路**,因為它的 tip 永遠是個字串:tip 上有本地分支就用分支名,沒有就用 hash。那時 `narrowed` 照樣送 `--onto`,而 HEAD 會 detach —— 對話框為此另外講明後果(ADR-0022),不是靠退回 interactive 迴避。

**四、清單只列 git 真的會重放的,所以 merge 不在裡面(這是採用的 B 案)。** merge commit 不進清單,因為沒有 `--rebase-merges` 的 rebase 從來不重放它們;把它列進去就是承諾一件 git 不會做的事,而那正是這整篇 ADR 要拆掉的東西。取而代之,對話框說出被壓掉幾個 merge,以及哪些本地分支會留在原地變成重複。被否決的 A 案與 C 案見下一節。

實測的行為值得原樣記著:範圍跨越 merge 時,`git rebase --onto` **靜默丟掉 merge commit**、把菱形壓成一條直線、把側枝的 commit 複製一份重放,而側枝的分支標籤仍指著原本那幾筆。範圍裡 4 個 commit,git 只重放 3 個。

**五、`narrowed` 這條捷徑只在清單是一條鏈時成立 —— 這是審查時發現的,不是設計出來的。** `git rebase --onto X <bound> <tip>` 排除的是 `<bound>` **以及 `<bound>` 走得到的一切**,而那等於「清單上排在它前面的那幾筆」**只在單一條鏈上**成立。merge 被壓掉之後,清單裝的是那個菱形的兩側首尾相接;拿側枝上的一筆當 bound,旁邊那些主線 commit 不是它的祖先,於是 git 照樣重放 —— 重放的正是使用者剛剛取消勾選的那幾筆,而且一聲不吭,清單的承諾就地作廢。

所以 `listIsChain` 是 `narrowed` 的**前提**,不是最佳化。不是一條鏈就退回 interactive:那個形式把每一筆都寫成 `pick` 或 `drop`,沒有第二種讀法。**這個坑是上一條直接長出來的** —— 把 merge 從清單拿掉的同時,也把「清單順序等於 ancestry 順序」這個原本成立的性質拿掉了。

**六、`GIT_SEQUENCE_EDITOR` 是丟給 shell 跑的,`GIT_ASKPASS` 是 exec 的。** git 把某些 hook 交給 shell —— `GIT_EDITOR` 與 `GIT_SEQUENCE_EDITOR` 是**指令字串**,不是 git 會 exec 的程式路徑;`GIT_ASKPASS` 相反,所以既有的 askpass helper 完全不需要處理這件事,照抄它就會壞。

Windows 路徑原樣交過去會在路上被拆掉:shell 把每個反斜線讀成跳脫字元,`D:\a\out\x.sh` 抵達時是 `D:aoutx.sh`,git 回報 editor "command not found"。修法在 `shellCommandPath`:換成正斜線(git 在 Windows 上帶的那個 shell 看得懂,而且正斜線不是跳脫字元),外面加引號承載含空白的路徑。

這一條單獨記一筆,是因為症狀指不到成因 —— 錯誤訊息說的是「找不到那個 editor」,而檔案就在那裡、權限也對。任何一個後來把 helper 掛到 `GIT_EDITOR` 或 `GIT_SEQUENCE_EDITOR` 上的人都會再踩一次。

**七、`git rebase <obj>` 與 `git rebase --onto <obj> <newUpstream> <tip>` 之間,量過之後沒有 fork-point 或 patch-id 的差別。** 這一條原本是以「有差別」登記進來的(#171 的討論串:`--onto` 不做 fork-point 偵測、也不做 patch-id 去重),量過不成立,記在這裡免得下一個人再登記一次。git 2.40.1:

- **fork-point**:`<upstream>` 一旦寫在命令列上,預設就是 `--no-fork-point`,兩種形式一樣。實測(`main` 被 rewind 掉一筆,`topic` 從被丟掉的那一筆分出去):`git rebase main` 重放 **2** 筆,把被丟掉的那一筆救了回來;`git rebase --onto main main topic` 也是 **2** 筆;只有明寫 `git rebase --fork-point main` 才是 **1** 筆。GING 兩種形式都把 `<obj>` 寫在命令列上,所以兩邊都沒有 fork-point 可言。
- **patch-id 去重**:兩種形式都做。實測 `--onto` 那一趟 git 自己印了 `dropping … patch contents already upstream`。比對的落點是新基底,而新基底在兩種形式裡是同一個 commit。

真正存在的差別只有兩件,而且兩件都正是使用者要求的:下界被挪到清單上的某一筆,以及 tip 被寫成分支名(ADR-0022)。

選單把這個範圍叫做**比對範圍**,而它現在**兩端都含在內**:使用者比對的那兩個 commit 都會被重放。`git rebase --onto X A B` 排除 `A`,所以送給 git 的 `<upstream>` 是**較舊那個選取的 parent**,不是那個選取本身 —— 拿選取當下界,就會把使用者親手挑的兩端之一丟在原地。merge 取第一個 parent(範圍是沿著那條線讀出來的);較舊那端是 root commit 時沒有下界可命名,`--onto` 表達不了,選單項退回普通的 rebase。

「diff 範圍」一度是候選,被否決:在 git 裡 diff 是**檔案層級**的東西(`git diff A B` 給的是一份 patch),而被搬走的是 commit。兩個 commit 之間可以有十個 commit 而 diff 是空的,那時「diff 範圍」聽起來像沒東西要搬。「比對範圍」指的是使用者實際做的那個動作,不指那份 patch。

## 考慮過但否決的方案

merge 的三個處理方式沿用 #171 的代號:A 拒絕、B 只列 git 會重放的(採用,見上一節)、C 用 `--rebase-merges` 保留拓撲。

**把「哪些 commit 會被搬」留給那行印出來的指令自己說。** 這是 ADR-0022 當時的答案(「使用者要自己看懂算出來的是什麼,對話框印出的那行指令就是為此存在」)。它在 merge 上直接破功:那行指令對「merge 被丟掉了、側枝被複製了一份、分支標籤留在原地」一個字都沒有說,而那些正是使用者最需要知道的。指令預覽答不了「哪些 commit」。**所以清單是加上去的,不是換掉它** —— 兩者都留著,而且都是必要的。

**A 案(拒絕):範圍裡有 merge 就不提供這個操作。** 最安全,也最沒用 —— merge 在真實歷史裡是常態,使用者想搬的那一段十之八九跨得過一個。把 merge 當禁區等於收掉大半功能,換一句不必解釋。

**C 案(保留拓撲):用 `--rebase-merges` 保住拓撲。** 這是「不壓平」的正解,而它把工作量跳一級:todo 的語法整組不同(`label` / `reset` / `merge`),對話框要表達的東西從一份清單變成一棵樹,而每一種勾選組合都得回答「這樣拓撲還接得起來嗎」。**它是延後,不是死掉。** 現在這份清單不含 merge、對話框把壓平的後果講出來 —— 這兩件事在 `--rebase-merges` 之下仍然是它的一個模式(使用者明確要求壓平時),不是要拆掉重來。

**把被取消勾選的那幾筆從 todo 裡直接刪掉,而不是寫成 `drop`。** 短,但把結果交給一個我們不控制的設定:git 會拿 todo 對照它預期的那組 commit(`rebase.missingCommitsCheck`),看得見的行它不會抱怨,漏掉的行則視設定值而定 —— 同一次操作在兩台機器上結果不同。全部寫出來,結果就與那個設定無關。

**範圍讀不完整時照樣讓清單可勾。** webview 只握著一段歷史,下界掉出那段時清單會短一截。**可勾的短清單是最壞的一種**:勾選會靜默丟掉使用者根本沒被展示過的 commit —— 短的方向才是危險的方向。所以那種情況下清單照顯示但不可勾,上方寫明原因,而 rebase 就跑它本來會跑的那一個。連範圍都算不出來時(例如側檢視按到一條落在已載入 commit 之外的分支)一筆都不列,同樣照跑原本的。

## 後果

- **ADR-0022 的一條「後果」原地失效,整篇維持 `accepted`。** 死掉的是「範圍可能不是一條直線……只是使用者要自己看懂算出來的是什麼」那一條。其餘部分沒有一條被推翻,而 `src/` 與 `tests/` 裡引用 ADR-0022 的那幾處引的正是那些活著的部分(指令印出來的與跑下去的必須是同一件事;`--onto` 不指向自己範圍的端點)。整篇改狀態會把那些引用指向一份不再那樣說的文件。做法比照 ADR-0020 對 ADR-0019 的處理 —— 整篇不改狀態,只在死掉的那一條上原地標記。多出來的是另外兩句:開頭一句說明分界,指令那一段一句說明它**沒有**被取代。ADR-0020 不需要那兩句,因為 ADR-0019 沒有哪一條會被誤讀成死掉;這裡有,而讓一條還活著的要求被當成死的,比讓死掉的那條多留一句更貴。

- **印出來的那行指令現在是勾選結果的函數,而且仍然是硬性要求。** 印出來的與跑下去的必須是同一件事,所以兩者都從同一個值(`RebasePickCommand`)讀出來,對話框沒有辦法印一個、跑另一個。`-S` 照舊跟著 `signing.commits` 出現在那行裡。勾選一改那行就跟著改:`--interactive` 會冒出來、下界會換人、全不勾時整行消失。範圍對話框還在選分支時,那行印的是 git 自己的 `<branch>` 佔位符,選單就是填它的地方(ADR-0022)。

- **兩個 commit 的手勢沒有被拿掉,它降級成種子。** CTRL/CMD 選兩個 commit 仍然決定範圍的兩端,清單就是從那個範圍讀出來的。變的是誰對使用者負責解釋這件事:以前是手勢加一行指令,現在是清單。

- **一份沒送到 git 的 todo 是錯誤,不是成功。** `git rebase -i` 拿不到我們寫的 todo 時會保留全部 commit 而且**正常結束** —— 那是一個「請丟掉這幾筆」的對話框最不能靜默產生的結果。helper 用掉 todo 檔就把它刪掉,`wasApplied` 據此回報,沒被用掉就報錯,而不是回報成功。

- **環境是整個工作階段固定的,所以哪一次 rebase 拿得到 todo 由檔案決定,不由變數決定。** simple-git 只設一次 client 的環境,不是每個指令設一次。`stage` 寫檔、helper 消費並刪除、`wasApplied` 回報有沒有發生。

- **`narrowed` 走既有的 `rebaseOnto` action,`interactive` 走新的 `rebaseInteractive`,而未動勾選走呼叫端原本那一個。** 三條路各自的參數與後果不同,共用同一個入口只會讓「未動勾選不改變任何事」變成需要證明的事,而不是看得出來的事。

- **這份清單只在 webview 裡算得出來。** 它讀的是已載入的 commit 與它們的 parent,所以「範圍有多長」受限於 loaded commit window(CONTEXT.md)。窗外的部分不是空的,是未知的,而未知一律往「不可勾」倒。
