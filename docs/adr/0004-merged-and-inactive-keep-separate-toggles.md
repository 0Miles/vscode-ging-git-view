# merged 與 inactive 保留兩個各自獨立的隱藏開關

側檢視有兩對 show/hide 命令,兩個 per-repo 狀態,兩個全域預設。隱藏是聯集:任一規則命中(且未被豁免)就藏。它們刻意不合併成單一「降噪」開關,也不改成子群組或排序沉底。

## 為什麼未來的讀者會困惑

兩個開關長得幾乎一樣、預設值都是隱藏、藏起來的分支高度重疊,看起來像是同一個功能做了兩次。下面這個反對意見在決策時被提出並權衡過,不是沒想到:

**inactive 的隱藏藏錯了東西。** inactive 且 merged 的是殭屍,藏它完全正確;但 inactive 而**未** merged 的,是你忘記的未完成工作 —— 那是分支清單裡最該被看見的一類,而這個機制正好把它藏起來,留下你最近碰過、本來就記得的那些。

保留它的理由:ADR-0002 決定常駐判定不認 squash / rebase,所以在 squash 工作流下,已合併的分支永遠不會被判 merged,只會慢慢變 inactive —— 那時 inactive 是唯一的降噪手段。砍掉它等於讓那批使用者失去降噪。

## 考慮過但否決的方案

**收進可摺疊子群組,退役兩個開關。** 每個遠端/本地 group 底部長出「已合併 (12)」「閒置 (5)」,預設摺疊。位置即狀態,不需要淡化、不需要開關、永遠看得到數量、一鍵展開仍可右鍵操作,而且「東西不見了」的困惑從根消失。否決是因為它要退役 `showInactiveByDefault` 與那對既有命令(breaking),且 group id 需重新設計以避免同名子群組撞號。

**單一「降噪」開關。** UI 最簡,但「只想看被遺忘的未合併工作」就做不到 —— 而那正是這兩個機制中唯一真正有行動價值的分類。

**不隱藏,只排序沉底加淡化。** 零困惑,但分支多的存放庫完全沒有降噪效果,而降噪正是 inactive 機制當初存在的理由。

## 後果

- 一個分支可能因為兩個不同的原因消失,而畫面上**沒有**任何計數或提示(維持與既有 inactive 相同的靜默行為)。使用者只能輪流試兩個開關來定位原因。這是明知的取捨。
- 兩個開關的豁免名單相同(head / 篩選選取中 / `alwaysShow`),所以 hidable 可以取聯集後只算一次。
