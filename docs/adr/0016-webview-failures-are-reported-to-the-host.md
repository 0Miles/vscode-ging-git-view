# Webview 的失敗一律回報給 host,抑制規則跟著介面走,不跟著失敗走

Webview 抓到的每個失敗都送一則 `reportError` 給 host,**每次都送**,不在 webview 端做任何過濾。抓的地方有三個:訊息處理外面的 `try`/`catch`(它知道是哪一則訊息)、`window` 的 `error` 與 `unhandledrejection`(它們什麼都不知道)。

Host 拿到之後餵給兩個介面,而兩個介面的抑制規則**刻意不同**:Output Channel 一模一樣的行只寫一次;使用者通知則每次都發,只限制「同時最多一則在螢幕上」。

## 為什麼未來的讀者會困惑

**「為什麼要抓三個地方?選一個不就好了?」**
因為兩種邊界各自漏掉對方涵蓋的一半。`try`/`catch` 涵蓋所有 host→webview 的路徑,但一旦處理過程把工作丟進 `setTimeout` 或 promise 鏈,延續的部分早就不在那個 call stack 上了,catch 抓不到。反過來,`window.onerror` 什麼都接得到 —— 代價是它接到的時候,「剛才在處理哪一則訊息」這件事已經不存在,而那個資訊是這條路唯一能寫進記錄的操作名稱。兩者都要,不是保險起見,是各自補對方的洞。

**「為什麼 catch 之後不 rethrow?」**
rethrow 會讓同一個失敗被 `window.onerror` 再回報一次,而且第二次那份**沒有**命令名稱 —— 用一則較差的記錄蓋掉較好的那則。取而代之的是 `console.error`:開著 Webview Developer Tools 的開發者仍拿到活的、可點擊的堆疊,和沒有這層 catch 時一模一樣。這是這張票明講要守住的東西(#39:別讓原本立刻會被發現的錯誤變得更難察覺)。

**「為什麼記錄去重,通知卻不去重?」**
因為兩個介面回答的是不同的問題。Output Channel 回答「到底什麼壞了」—— 第二份一模一樣的堆疊一個字都沒多說,而渲染迴圈裡的失敗會以事件的頻率重複,把周圍的 git 指令沖掉;所以完全相同的那一行只寫一次。使用者通知回答的是「我剛才做的事完成了嗎」—— 每一次失敗都是一次新的「沒有」,把重複壓掉就等於對第二次以後的失敗重新裝聾,也就是這張票要修的那個病。通知要防的不是重複,是**堆疊**:所以限制的是同時在螢幕上的數量,不是總次數。

**「為什麼抑制不做在 webview 端?那裡最省事。」**
省的是一次 postMessage,買到的是一個鍵同時決定兩個介面 —— 而它們要的規則不一樣。抑制規則必須和它治理的介面住在一起,兩個介面在 host,所以規則也在 host;webview 只負責把失敗描述完整、每次都說。

## 考慮過但否決的方案

**在 webview 端去重(第一版的做法)。** 一個 key(origin + 命令 + 訊息 + 堆疊)決定「要不要送」。否決是因為它把記錄與通知綁成同一件事:同一個 bug 第二次發生時,兩個介面同時靜默 —— 使用者第二次打開同一個對話框,又回到什麼都不知道。#39 的原句是「至少讓使用者知道這次操作沒有完成」,而第二次也是一次。

**只有 `origin: "message"` 才通知。** 理由曾經是「只有它說得出是哪個操作」。否決是因為它把「使用者觸發」錯認成「來自 host 訊息」:面板上絕大多數使用者動作是 webview 自己的 click / menu handler,它們丟出的例外走 `window.onerror`,`origin` 是 `uncaught`。照這條規則,背景自動 refresh 失敗會提示,而使用者親手按下去的按鈕失敗反而不提示 —— 恰好是票裡那句「也許只在『使用者剛觸發的動作』失敗時才提示」的反面。

**在 webview 自己跳錯誤對話框,host 只記錄。** 訊息就在使用者的注意力所在之處。否決有二:一是壞掉的很可能正是 webview 的 DOM,把「告知失敗」交給正在失敗的那一層,是拿它的健康當前提;二是 webview 的對話框一次只有一個,錯誤框會直接蓋掉剛剛渲染到一半的那個對話框,而且它無法提供「開啟 Output Channel」的去處。VS Code 的通知兩件事都沒有。

**做成通用的 webview 日誌通道(`log` request,分 level)。** `reportError` 的形狀離它只差一點。否決是因為今天沒有任何東西需要它,而這個頻道現在的內容是 git 指令 —— 一條隨手可用的 log 管線,會把它變成雜訊場,反而讓真正的失敗更難被看見。要加時再加,加的人得先說明為什麼那些訊息值得和 git 指令並列。

**通知不設任何上限。** 這是「完全靜默」的反面極端:一個迴圈裡的失敗會疊出一整排通知,而使用者學到的是把通知關掉,回到靜默 —— 只是這次是他自己關的。

**Output Channel 也不去重。** log 就該是 log,重複本身也是資訊。否決是因為同一個迴圈能在幾秒內寫進上千行,把這個頻道的主要內容沖掉;而第一次那筆已經帶著完整堆疊,bug 回報要的就是它。

## 後果

- **「它一直在發生」這件事讀不出來。** 記錄只留第一次,而通知不說次數。代價已知,換的是一個還讀得懂的頻道。堆疊只要有一格不同,就是另一筆,會照樣寫。
- **沒被處理掉的通知會壓住後面的通知。** 「同時最多一則」是靠 `showErrorMessage` 的 promise 決定的,而它要等使用者關掉才 resolve。使用者放著不管,期間的失敗就只進記錄 —— 螢幕上那則未讀的通知已經在說同一件事了。
- **Webview 每次失敗都送一則 postMessage。** 迴圈型失敗會以事件的頻率送,host 端丟掉重複的成本很低,但這條路確實比第一版吵。抑制住在該住的地方,值這個價。
- **記錄的去重集合活在 extension session,不隨面板重載清空。** 重載後同一個失敗不會再寫一行 —— 但第一行還在頻道裡,沒有東西不見。
- **Output Channel 從此不只有 git 指令。** 它現在也是 webview 失敗的唯一去處,那個「這個頻道只記 host 跑的 git 指令」的假設不再成立。
- **通知不指名是哪個操作。** 訊息名稱(`showBranchCleanup`)是內部字彙,對使用者沒有意義,所以它只進記錄。使用者看到的是「有東西沒完成 + 去哪看」。
- **`reportError` 是 `mutatesRepo: false`。** 它不碰 repo,不能讓 file watcher 靜音。
- **半套用的狀態仍然留在畫面上。** 這裡新增的是「說出來」,不是回復 —— 沒有任何機制知道那則訊息改到一半的是什麼、該怎麼還原。使用者被告知後的正常出路仍是 refresh。
- **模組載入期間丟出的例外仍然無痕跡。** reporter 是 `main.ts` 的第一個 statement,但 import 進來的模組比它更早求值。#39 的實例(呼叫時才 ReferenceError)有涵蓋,import-time 的沒有。
- **host 自己的 handler 例外不在這條路上。** `webviewBridge` 目前把 handler 丟出的例外重新丟出去,落到 extension host 的 unhandled rejection,同樣不進這個頻道。那是同一類問題的另一半,但不在這張票的範圍內。
