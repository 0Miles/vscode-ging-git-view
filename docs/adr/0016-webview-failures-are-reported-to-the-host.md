# Webview 的失敗一律回報給 host,但只有訊息處理那條路提示使用者

Webview 抓到的每個例外都送一則 `reportError` 給 host,由 host 寫進 GING 的 Output Channel。抓的地方有三個:訊息處理外面的 `try`/`catch`(它知道是哪一則訊息)、`window` 的 `error` 與 `unhandledrejection`(它們什麼都不知道)。**只有**訊息處理那條路會另外跳一則錯誤通知給使用者;另外兩條只留記錄。

## 為什麼未來的讀者會困惑

**「為什麼要抓三個地方?選一個不就好了?」**
因為兩種邊界各自漏掉對方涵蓋的一半。`try`/`catch` 涵蓋所有 host→webview 的路徑,但一旦處理過程把工作丟進 `setTimeout` 或 promise 鏈,延續的部分早就不在那個 call stack 上了,catch 抓不到。反過來,`window.onerror` 什麼都接得到 —— 代價是它接到的時候,「剛才在處理哪一則訊息」這件事已經不存在。而那個資訊正是把「有東西壞了」變成「這次操作沒有完成」的唯一材料。兩者都要,不是保險起見,是各自補對方的洞。

**「為什麼 catch 之後不 rethrow?」**
rethrow 會讓同一個失敗被 `window.onerror` 再回報一次,而且第二次那份**沒有**命令名稱 —— 用一則較差的記錄蓋掉較好的那則。取而代之的是 `console.error`:開著 Webview Developer Tools 的開發者仍拿到活的、可點擊的堆疊,和沒有這層 catch 時一模一樣。這是這張票明講要守住的東西(#39:別讓原本立刻會被發現的錯誤變得更難察覺)。

**「為什麼提示只給訊息處理那一條?」**
因為只有它能說出使用者聽得懂的話。訊息處理失敗 = 面板剛才被要求套用某件事、套到一半停住 —— 這正是「半套用的狀態不要假裝成功」所指的那個狀態。另外兩條抓到的東西,連是哪個動作都答不出來,而且可能來自每次滑鼠移動就重跑一次的程式碼;為它們跳通知只會教會使用者忽略通知。

## 考慮過但否決的方案

**在 webview 自己跳錯誤對話框,host 只記錄。** 訊息就在使用者的注意力所在之處。否決有二:一是壞掉的很可能正是 webview 的 DOM,把「告知失敗」這件事交給正在失敗的那一層,是拿它的健康當前提;二是 webview 的對話框一次只有一個,錯誤框會直接蓋掉剛剛渲染到一半的那個對話框,而且它無法提供「開啟 Output Channel」的去處。VS Code 的通知兩件事都沒有。

**做成通用的 webview 日誌通道(`log` request,分 level)。** `reportError` 的形狀離它只差一點。否決是因為今天沒有任何東西需要它,而這個頻道現在的內容是 git 指令 —— 一條隨手可用的 log 管線,會把它變成雜訊場,反而讓真正的失敗更難被看見。要加時再加,加的人得先說明為什麼那些訊息值得和 git 指令並列。

**每個失敗都通知。** 這是「完全靜默」的反面極端。一個渲染迴圈裡的失敗會以事件的頻率重複,通知風暴的下場是使用者關掉通知,回到靜默 —— 只是這次是他自己關的。

**每個失敗都寫進 Output Channel,不去重。** log 就該是 log,重複本身也是資訊。否決是因為同一個迴圈能在幾秒內寫進上千行,把這個頻道的主要內容(git 指令)沖掉。

## 後果

- **同一個失敗一個 webview session 內只說一次。** 去重的鍵是 origin + 命令 + 訊息 + 堆疊,住在 webview 端(順帶省掉 postMessage 往返)。第一次就帶著完整堆疊,那是 bug 回報需要的東西;之後完全相同的那些直接丟掉 —— 代價是「它一直在發生」這件事讀不出來。面板重載會清空這個集合。
- **Output Channel 從此不只有 git 指令。** 它現在也是 webview 失敗的唯一去處,所以那個「這個頻道只記 host 跑的 git 指令」的假設不再成立。
- **通知不指名是哪個操作。** 訊息名稱(`showBranchCleanup`)是內部字彙,對使用者沒有意義,所以它只進記錄。使用者看到的是「有件事沒完成 + 去哪看」。
- **`reportError` 是 `mutatesRepo: false`。** 它不碰 repo,不能讓 file watcher 靜音。
- **半套用的狀態仍然留在畫面上。** 這裡新增的是「說出來」,不是回復 —— 沒有任何機制知道那則訊息改到一半的是什麼、該怎麼還原。使用者被告知後的正常出路仍是 refresh。
- **host 自己的 handler 例外不在這條路上。** `webviewBridge` 目前把 handler 丟出的例外重新丟出去,落到 extension host 的 unhandled rejection,同樣不進這個頻道。那是同一類問題的另一半,但不在這張票的範圍內。
