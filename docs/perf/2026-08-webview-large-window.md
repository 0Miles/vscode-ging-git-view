# webview 在大載入視窗下慢在哪(2026-08,ticket #96)

調查報告。**交付物是歸因與數字,不是修改** —— 這份文件沒有動到任何 production 程式碼。

## 結論先行

四個候選裡,**沒有一個是瓶頸**。三個小到可以忽略,一個(版面走訪)有真的超線性但佔比太低,修了也看不見。

### 形狀

沿用 ADR-0020 的形狀:本機 http server + 真正的瀏覽器分頁 + 從外面用 JS 驅動。

1. `esbuild` 把 **production 的 `src/webview/graph.ts`** 與一組由它機器生成的變體打包成一支 IIFE bundle(`target: "es6"`,與 `esbuild.js` 裡 webview 那支一致)。
2. 一個 `index.html`,CSS **從 `media/main.css` 抄過來**(commit table 那一段連 `.autoLayout` / `.fixedLayout` 規則一起),讓表格的版面成本是出貨的那一個。

4. 用瀏覽器工具開該 URL,`javascript_tool` 呼叫 `window.BENCH.*` 並回傳 JSON。

量測用的檔案全部放在 repo 外的 scratchpad,跑完即刪;`git status` 除了這份報告以外是乾淨的。

### 變體怎麼生成

歸因要能站得住,變體就**不能是手抄的**。生成腳本讀 `src/webview/graph.ts`,做定點字串替換,**任何一條替換沒有命中或命中超過一次就 throw** —— 一條被靜默略過的替換會讓歸因變成謊話。

| 變體 | 改了什麼                                                         |
| ---- | ---------------------------------------------------------------- |
| `V0` | production 原文,只把 type-only import 換成本地 shim              |
| `V1` | `findStart()` 改用單調游標,不再每次從 0 重掃                     |
| `V2` | `getPointConnectingTo()` 改查索引 `Map`,不再線性掃 `connections` |
| `V3` | `addLine()` 不再配置那個 `Line` 物件(只累加計數)                 |
| `V4` | `V0` + 操作計數器(不改行為)                                      |
| `V5` | `V1` + `V2`                                                      |
| `V8` | `V1` + `V3`                                                      |
| `V7` | `V0` + `render()` 內部的分段計時                                 |

`V1` 的正確性不靠測試靠論證:「這個 vertex 做完了」是**單調**的 —— `getNextParent()` 只會因 `registerParentProcessed()` 往前走,`isNotOnBranch()` 只會因 `addToBranch()` 由 true 變 false,兩者都不會回頭。所以被游標略過的 vertex 永遠可以略過。

**每個不破壞行為的變體都跟 `V0` 對過渲染結果**:在 `adr` / `dense` / `open` / `linear` / `reused` / `reusedDense` / `wide` 七種拓撲、1500 列下,`V1`、`V2`、`V4`、`V5` 產生的 `#commitGraph` innerHTML 與 `V0` **逐字元相同**。`V3` / `V8` 蓄意破壞渲染(沒有 `Line` 物件可走),只用來取版面走訪的時間。

### 合成歷史

一次生成 13,000 筆(最舊在前,再反轉成 `git log` 給 webview 的最新在前),400 個 ref 灑在較新的那一段 —— 對齊 ADR-0020 那個 20,800 commit / 401 ref 的存放庫。「載入視窗 N」就是取前 N 筆,與後端 `--max-count` 的語意一致。

拓撲是參數,因為**歸因的答案會隨拓撲改變**:

| 拓撲                     | 形狀                                                                    |
| ------------------------ | ----------------------------------------------------------------------- |
| `adr`                    | 主線 + 每 50 筆一條長度 3 的 side branch 並 merge back(ADR-0020 的形狀) |
| `dense`                  | 同上但每 10 筆一次                                                      |
| `reused` / `reusedDense` | `adr` / `dense`,**外加 side branch 在被合併之後繼續長 commit**          |
| `open`                   | 主線 + 24 條長期不合併的分支                                            |
| `wide`                   | 40 條長期分支 + 每 10 筆一次「合併後繼續長」的 side branch              |
| `linear`                 | 純線性                                                                  |

**`reused` 這個 motif 是必要的,不是裝飾。** 在沒有它的拓撲裡,`determinePath()` 的 merge 分支入口條件(`!parentVertex.isNotOnBranch()`)**一次都不成立** —— 量到的 `getPointConnectingTo` 呼叫次數是 **0**。第二個 parent 得在別的走訪裡先被排上某條 branch,那個 merge 才會走 merge 那一支;而讓它先被排上的,正是「合併後分支繼續長 commit」把 side tip 頂到 merge 上方。這也正是 ADR-0020 點名、且移除後既有列改變率歸零的同一個 motif。

主表用 `reusedDense`(四個候選都會被觸發);`wide` 用來做候選 1 的對抗性上界。

### `saveState()` 為什麼可以在瀏覽器裡量

VS Code 的 `acquireVsCodeApi()` 是在 webview 的 host 頁面裡即時組出來的。逐字引自 `resources/app/out/vs/workbench/contrib/webview/browser/pre/index.html`(VS Code 1.134.0):

```js
setState: function(newState) {
    state = newState;
    doPostMessage('do-update-state', JSON.stringify(newState));
    return newState;
},
```

所以 webview 這條執行緒付的是 `JSON.stringify(整份 state)` 加上把結果字串 postMessage 出去。兩者都在一般瀏覽器裡可量:`JSON.stringify` 直接量,跨 realm 的 postMessage 用 `MessageChannel` 量(那是下界,少了 iframe 邊界的部分)。

### `renderTable` 用替身

`renderTable()` 是 `GitGraphView` 的 private method,要動它得把整個 webview 立起來。這裡用的是形狀相符的替身(相同的 tag 結構、相同的 `escapeHtml`、相同的欄位)。**校準結果:替身在 3000 列量到 40.1–42.8 ms,ADR-0020 對真正那支方法量到 41 ms。** 替身可信。

## 超線性的歸因

**三個成因候選裡,`findStart()` 每次從頭重掃是主導的那一個。它是唯一一個單獨拿掉就讓曲線變回線性的。**

### 證據一:計數器(與平台、GC 無關)

`reusedDense`:

|     N | `findStart` 掃描步數 | `getPointConnectingTo` 比較次數 | `addLine` 呼叫次數 |
| ----: | -------------------: | ------------------------------: | -----------------: |
|  1500 |              225,603 |                             299 |              2,547 |
|  3000 |              901,203 |                             599 |              5,097 |
|  6000 |            3,602,403 |                           1,199 |             10,197 |
| 12000 |       **14,404,803** |                       **2,399** |             20,397 |

列數 8 倍 → `findStart` 步數 **64 倍**,精確的 O(N²)。另外兩個都是線性,而且絕對量差了三到四個數量級。

`findStart()` 被呼叫的次數本身就與分支數同階(每條 branch 一次、每個待處理的 parent 一次),每次又從 index 0 掃到第一個未完成的 vertex —— 已經完成的前綴被重掃了 branch 數那麼多遍。

### 證據二:逐一停用,看曲線哪一次變回線性

見候選 1 的表:`V1` 的指數塌到 1.00–1.12,`V2` 與 `V3` 完全沒有改變曲線形狀。12000 列下 `V1` 比 `V0` 快 **6.4 倍**(5.7 ms vs 36.3 ms)。

### `getPointConnectingTo` 的內層線性搜尋:不只無關,而且「修」了會更慢

那個 `connections` 陣列的長度是**該列的 lane 數**,不是列數。實測每次呼叫的比較次數:

| 拓撲                         | 每次呼叫平均比較次數 | 12000 列的總比較次數 |
| ---------------------------- | -------------------: | -------------------: |
| `reusedDense`                |                  2.0 |                2,399 |
| `wide`(40 條並行分支,對抗性) |                 40.7 |               24,420 |

即使刻意做出 40 條並行 lane,總比較次數也只有兩萬四千次。而換成 `Map` 索引(`V2`)反而**變慢 1.2 到 2.8 倍** —— 為每個 vertex 配置 `Map` 的成本遠高於掃兩個元素:

| N=12000       |    `V0` |     `V2` |
| ------------- | ------: | -------: |
| `reusedDense` | 36.3 ms |  41.9 ms |
| `wide`        | 47.0 ms | 130.2 ms |

**這是這次調查裡最該記下來的一條:候選 1b 是三個成因候選裡唯一一個「看起來最像效能問題」的,而它是三個裡唯一一個修了會退步的。**

### 每列一個 `Line` 物件:不造成超線性,但在「很多長期分支」的存放庫裡是主導項

它是 O(lane 數 × N) —— 線性,但常數由拓撲決定:

| 拓撲                  | 12000 列的 `addLine` 次數 | 相對列數 |
| --------------------- | ------------------------: | -------: |
| `adr`                 |                    12,959 |     1.1× |
| `reusedDense`         |                    20,397 |     1.7× |
| `open`(24 條長期分支) |                   294,934 |    24.6× |
| `wide`(40 條長期分支) |                   480,558 |    40.0× |

在 `wide` 下,`V1` 單獨拿掉救不了(指數仍是 1.82),`V3` 單獨拿掉也救不了(1.71),**兩個一起(`V8`)才把指數壓到 1.29**,絕對值從 47.0 ms 降到 14.2 ms(3.3 倍)。

所以完整的歸因是:

- **超線性由 `findStart()` 造成,而且只由它造成。** 這一條與拓撲無關。
- **在有大量長期未合併分支的存放庫裡,還有一個係數很大的線性項**(每列每分支一個 `Line` 物件),它不是超線性,但在 `wide` 下絕對值比 `findStart` 那一項更大。
- **`getPointConnectingTo` 在任何拓撲下都不是成本。**

## 那個沒有人列進候選的第五件事

`renderTable()` 之後,同一次重繪裡發生了**兩次**對整張表格的強制同步版面計算:

1. `makeTableResizable()` —— 先把 resize handle 寫進 5 個表頭 cell,再讀 `cols[0].offsetWidth`。寫完再讀就是一次強制同步版面,而且是這張新表格的第一次。
2. `renderGraph()` —— 讀 `colHeadersElem.clientHeight` 與 `tableElem.children[0].clientHeight` 來推 `grid.y`。而 `makeTableResizable()` 在上一步的讀之後**又寫了** `cols[0].style.padding`,所以這一讀是第二次完整版面。

實測(3000 列):

|                             | `autoLayout`(預設) | `fixedLayout` |
| --------------------------- | -----------------: | ------------: |
| `innerHTML` 之後第一次版面  |           237.9 ms |      237.4 ms |
| 緊接著再讀一次(版面已乾淨)  |        **0.00 ms** |   **0.00 ms** |
| 寫一次表頭 padding 之後再讀 |        **80.7 ms** |   **18.4 ms** |

(這一格與上面第 123 行那張表的 61.2 ms 量的是同一件事,差在方法:這裡是在活表上做的合成量測,那裡是一次完整重繪的分段計時。#104 後來重量到 79.2 ms,與這裡一致。三個數字都對,量的邊界不同。)

「版面已乾淨時再讀一次是 0.00 ms」這個對照證明量到的是**版面計算本身**,不是讀屬性的開銷。

兩者的性質不同,不可混為一談:

- **第一次(237.9 ms)不是浪費。** 3000 列進了 document,瀏覽器在畫出來之前本來就得排版它。同步強制它只是讓它「擋住」而不是「稍後發生」。要拿掉它只有一條路:**不要把 N 列都放進 document**(虛擬化)。
- **第二次(80.7 ms,佔一次重繪 15–18%)是額外的**,它的成因是讀→寫→讀的順序,而且在 `fixedLayout` 下只要 18.4 ms。這一段是可以動的。

`fixedLayout` 只在使用者拖過欄寬之後才會啟用(`makeTableResizable` 裡 `columnWidths !== null`),所以**出貨預設走的是比較貴的那一條**。整體而言 `fixedLayout` 讓一次 3000 列的重繪從 328.7 ms 降到 264.7 ms(約 20%)。

另外 ADR-0020 提過的「每個捲動 tick 一次的強制同步版面」(`observeWebviewScroll` 讀 `document.body.offsetHeight`):在版面乾淨時是 **0.00 ms**。它只有在同一個 tick 裡有人先寫了才會變貴。**不要為了它做節流**,那是修錯東西。

## 建議優先序

**都不在這張票裡做。** 以下只列出來,各自另開票。

1. **虛擬化 commit 表格(只把可視範圍附近的列放進 document)。**
   針對的是 316 ms / 76.7%(3000 列)裡的絕大部分,外加 `renderTable` 的 59.6 ms / 14.5%。這是唯一一個能改變數量級的方向,也是唯一一個成本相稱的大工程。**動手之前必須先確認它與 ADR-0020 那條「版面是已載入清單的純函數」的性質相容** —— 虛擬化改的是「畫出哪幾列」,不是「版面怎麼算」,兩者可以分開,但那要另外論證。

2. ~~**拿掉第二次強制同步版面。**~~ **已做(#104),但結果與這裡的預期不同,見下。**
   原文:針對 61.2 ms / 14.9%(3000 列)。做法是把 `makeTableResizable()` 與 `renderGraph()` 的讀集中在寫之前,或讓表頭 padding 不需要先讀 `offsetWidth`。投入產出比最好的一項,而且與 1 互不衝突(虛擬化之後它會自動縮小,但不會消失)。這件事與 ticket #94 是同一片地,應該合併考慮。

   **實際做出來的是:把 padding 的寫入延後到 `renderGraph` 的讀之後。**「把讀集中在寫之前」量過之後行不通 —— `renderTable` 的 `innerHTML` 已經把版面弄髒,讀放哪裡都要付一次完整版面,而 padding 的寫相依於那次讀。

   **而收益比這裡預期的窄。** 強制**同步**版面確實從 79.2 ms 降到 0.00,但**版面計算本身沒有消失** —— 它搬到瀏覽器自己的 rendering step(重繪後的對照讀由 22.3 跳到 116.0),總版面工作量前後只差 0.6%。真正買到的是**重繪的 blocking task 少 20%**(534.8 → 426.5 ms),主執行緒早約 100 ms 交還;**time-to-paint 沒有改善**。上面那句「投入產出比最好」在這個限定下仍然成立,但它指的是回應性,不是畫面速度。

   順帶:修完之後,`fixedLayout` 原本快 20% 的優勢**沒有了**(兩支都只有一次表格版面)。

3. **`findStart()` 改單調游標。**
   針對 3.2 ms / 0.8%(3000 列),12000 列下 36.3 → 5.7 ms。**排這麼後面不是因為它不真,是因為它佔比太低。** 但它是四個候選裡唯一一個「已經證明有效、行為完全不變、改動小到可以逐字檢查」的:七種拓撲下渲染輸出與現況逐字元相同,正確性有單調性的論證撐著。如果想在動大工程之前先拿一個乾淨的、零風險的改動,這是那一個。

4. **不要動 `getPointConnectingTo`。** 已經量過,改成 `Map` 索引會慢 1.2–2.8 倍。這一條寫進來是為了讓下一個看到那個內層迴圈的人撞到數字,而不是撞到直覺。

5. **`Line` 物件的每列配置:先確認自己的使用者長什麼樣再說。** 只有在「很多長期未合併分支」的存放庫裡才值得(`wide` 下 12000 列省 3.3 倍),在主線型存放庫裡省不到東西。動它之前應該先有真實存放庫的 lane 數分布。

6. **`saveState()`、`Graph.render()`、soft refresh 深度比對:不要動。** 三者在 3000 筆下合計 11.4 ms,佔 2.8%。特別是深度比對,量到 0.0 ms;它在自己那條路徑上被結構化複製壓過 20 倍以上,任何針對它的優化都會被 IPC 淹掉。

## 量測不足以支撐的地方

- **沒有涵蓋 paint / composite。** 分段裡的「版面」到 layout 為止。原本用 `requestAnimationFrame` 量整個 frame,但這個瀏覽器分頁的 rAF 節奏不穩(300 列量到 277 ms,不可能),數字不可信,已捨棄。所以真實的重繪只會**比這裡列的更慢**,不會更快;各段的相對佔比不受影響。
- **`renderTable` 是替身不是本尊。** 已對 ADR-0020 的 41 ms 校準過(替身 40.1–42.8 ms),但真正的 `renderTable()` 還做了 emoji 短碼替換、ancestor 集合計算、avatar、tooltip、signature —— 這些只會讓它更貴。它排在第 2 名,不影響結論。
- **絕對值跨回合有 ±25% 漂移**(DOM 與版面那幾段,GC 與熱節流)。同一回合內的**佔比**跨回合穩定在 ±2 個百分點,所以結論建立在佔比上,不建立在單一 ms 讀數上。
- **拓撲是合成的,不是真存放庫。** 候選 1 的歸因**會隨拓撲改變**(見上),這一點已經據實寫進歸因裡,但「哪一種拓撲比較像 GING 的使用者」這個問題,這次量測沒有回答,也回答不了。要回答它需要真實存放庫的 lane 數分布。
- **`saveState()` 的 postMessage 是下界。** 用 `MessageChannel` 量,少了 VS Code 那層 iframe 邊界。以 3000 筆 0.1–0.2 ms 的量級來說,補上也改不了任何結論。
- **`open` / `wide` 這兩種拓撲下,`V5`(V1+V2)的讀數雜訊很大**(6000 列 17.9 ms、12000 列 75.7 ms,跨回合不穩)。那是 `V2` 的 `Map` 配置在餵 GC。`V2` 的結論是「更慢」,方向明確;但它慢多少,這裡給不出精確的數。
