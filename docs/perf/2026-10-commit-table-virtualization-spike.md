# commit 表格虛擬化值不值得做(2026-10,ticket #115)

限時 spike。**交付物是量測、相容性論證與建議,不是實作** —— 這份文件沒有動到任何 production 程式碼;原型是丟棄式的,放在 repo 外。

## 結論先行

**值得做,但不要一次做完。建議「先做一部分」:先把鍵盤、焦點、Find 與 inline CDV 從「讀 DOM 列」改成「讀 commit 索引」,再只對 commit 表格的列做固定列高的視窗化,SVG 先不動。** 要不要做由 maintainer 決定;若決定做,拆票方式見文末。

依據:

|                                       |         300 筆 |        3000 筆 |            10000 筆 |
| ------------------------------------- | -------------: | -------------: | ------------------: |
| 現況:一次重繪的 blocking task(中位數) |        55.9 ms |     **523 ms** |         **1810 ms** |
| 現況:捲動每幀間隔(中位數 / p90)       | 16.7 / 16.9 ms | 17.8 / 39.8 ms | **55 / 107–127 ms** |
| 現況:document 節點數                  |          2,232 |         21,532 |              71,560 |
| 原型:視窗化後一次渲染                 |   18.0–19.3 ms |   13.9–17.7 ms |         9.4–19.6 ms |
| 原型:捲動每幀間隔(中位數 / p90)       |              — | 16.6 / 17.4 ms |      16.7 / 17.3 ms |
| 原型:document 節點數                  |            953 |            953 |                 953 |

- **出廠的 300 筆沒有問題**(56 ms、捲動滿 60 fps)。問題只在 loaded commit window 被撐大之後 —— 而自動載入預設開啟、Find 也會為了觸及匹配而擴大視窗,所以撐到幾千筆是走得到的路,不是邊角。
- **10000 筆時,捲動本身就掉到約 18 fps**(每幀 55 ms)。這一項不是重繪,是使用者每一次滾輪都會碰到的;關掉 sticky 表頭、隱藏 SVG 都不改變它(見下),它跟著 DOM 大小走。原型把它拉回 16.7 ms。
- **虛擬化與 ADR-0020 相容,不取代它** —— 條件是版面走訪仍然對整個載入清單做。論證見下。
- **最便宜的替代方案(`content-visibility: auto`)量過,沒有效果。** 它對表格列不起作用。

## 原型:只把視窗附近的列放進 document

### 做法

丟棄式,不碰 bundle 的程式碼。先讓真的 bundle 把 N 列畫出來,**逐字取下它產出的每一列 `outerHTML`** 與表頭,所以每列的 markup、class、CSS 規則就是出貨的那一份。然後:

- `<tbody>` = 表頭列 + 上方 spacer 列(`start × 列高`) + 第 `start` 到 `start+120` 列 + 下方 spacer 列。120 列是 800 px 視窗約 30 列可見的 4 倍(含 overscan)。
- 列高用 `renderGraph` 自己的算法:`(表格高 − 表頭高) / 列數`,量到 24.00004 px。
- 兩種 SVG:`window` 只留 `cy` 落在視窗內的 vertex(`<circle>`),path 整條保留;`full` 保留整份 SVG。
- 兩種表格版面:`fixedLayout`(寬度取自全量渲染時量到的表頭寬)與 `autoLayout`。

每組量完都把 bundle 原本那個 `<svg>` 節點放回去 —— `Graph` 持有它的參照,換掉的話之後的重繪會畫進一個脫離 document 的節點,數字會變得好看而且是錯的(第一輪就踩到了,那一輪的數字已丟棄)。

### 數字

視窗化,`fixedLayout`,SVG `window`。每格 3 次;移動 = 在整個清單上均勻取 30 個位置重設視窗:

|                      | 300          | 3000         | 10000        |
| -------------------- | ------------ | ------------ | ------------ |
| 初次渲染(不含拆舊表) | 18.0–19.3 ms | 13.9–17.7 ms | 9.4–19.6 ms  |
| 每次移動視窗,中位數  | 16.5–16.9 ms | 18.4–19.3 ms | 11.8–15.7 ms |
| 每次移動視窗,最大    | 26.3–56.8 ms | 39.8–58.8 ms | 23–54.3 ms   |
| document 節點        | 953          | 953          | 953          |

一次移動視窗的組成(3000 筆典型):表格 `innerHTML` 4.4 ms + SVG 1.8 ms + 版面 12.1 ms。版面幾乎全是**新節點**的樣式與排版 —— 同一個 120 列的視窗只改寬度重排是 0.6 ms(`autoLayout` 2.8 ms),10000 筆的現況是 145–238 ms。所以一次移動大約一幀:實作時視窗不該每個捲動 tick 都重建,要靠 overscan 讓它每捲過幾十列才動一次,或回收列節點而不是整段 `innerHTML`。

**成本與 N 無關,這正是重點。** 同一個方法把 N 列全部放進去(`protoAll`)是 42.3 / 377–526 / 1231–2070 ms,與上面現況的 bundle 數字同一個量級,校準了原型量到的是同一件事。

幾個副產品:

- **對齊**:捲到第 9940 列(共 10000),該列中線在 viewport 424.0 px,最近的 vertex 中線 423.8 px。spacer 不會讓 SVG 與列錯位。
- **sticky 表頭(#206)**:捲到 `scrollY` 70320,表頭 `th` 的 top 是 32 px(= `--ging-controls-height`);`scrollIntoView({ block: "start" })` 把列放在 63.2 px,剛好在表頭底 62.4 px 下方 —— `scroll-margin-top` 照常生效。頁面高度 72,103 px 對 72,102 px,頁尾位置不變。
- **保留整份 SVG、只視窗化表格**:初次渲染 42.7 ms(3000)/ 76.9 ms(10000),節點 3,832 / 10,832。比完整視窗化貴,但仍是現況的 1/12 與 1/24。
- **`autoLayout` 不能跟著視窗化**:欄寬由「目前在 document 裡的列」決定。30 個視窗位置下,3000 筆量到 2 組不同的表頭寬、10000 筆量到 3 組(描述欄 895–901 px、日期欄 102–108 px)。合成資料的作者名只有 5 種、日期格式一致,真實存放庫只會抖得更兇。捲動時欄位左右跳,這不能出貨。

### 估一次虛擬化之後的完整重繪

原型量的是 DOM 與版面。真正的重繪還有與 N 成正比的純 JS:2026-08 報告在 3000 筆量到 `saveState` 1.9 + `commitLookup` 0.3 + 版面走訪 3.2 ms。所以:

- 3000 筆:約 **17 + 5 ≈ 22–30 ms**,現況 523 ms,約 **20 倍**。
- 10000 筆:版面走訪在 6000 / 12000 筆是 9.9 / 36.3 ms,內插約 25 ms;加上 `saveState` 約 5 ms,約 **50–60 ms**,現況 1810 ms,約 **30 倍**。

這是估計,不是量測:沒有人把這兩段接在一起跑過。

## 更便宜的方案,量過或想過

**`content-visibility: auto` 加在 `tr.commit` 上 —— 沒有效果。** 3000 筆,交錯各 3 次:原樣 506.5 / 553.8 / 593.6 ms,加上之後 500.3 / 560.1 / 714.2 ms。這符合規格:size / layout containment 不適用於表格內部的 box(`table-row` 等),所以 `content-visibility` 在 `tr` 上什麼都跳不過。拆成多個 `<tbody>` 同理。要用它就得先把表格換成非 table 的版面,那比虛擬化還大。

**只在超過一定列數時啟用。** 這是對的,但門檻應該只決定「視窗有多大」,不應該決定「走哪一條程式碼」。視窗大小 = `min(N, 門檻)` 時,低於門檻就是「視窗涵蓋全部」—— 同一條路徑,行為與今天逐像素相同,jsdom 的測試也不用知道虛擬化存在(現有 31 個 webview 測試檔裡有 64 處直接查 `tr.commit`)。反過來,若門檻切換的是兩套鍵盤、兩套 Find,那就是 ADR-0014 否決過的「一顆鍵兩種意思」換一個地方再發生一次。

**分批漸進渲染**(先畫第一屏,其餘用 idle callback 補)。總工作量不變,只是把 blocking 拆碎;而在補完之前,`scrollIntoView`、Find、焦點還原面對的是一張還沒長完的表,與虛擬化要解的問題一樣多,收益卻只有一半。不建議。

## 與 ADR-0020 相容嗎

**相容,不取代。** 但相容是有條件的,而那個條件正是 ADR-0020 否決過的方案的邊界。

ADR-0020 保住的性質是:**版面是已載入清單的純函數** —— 同一份清單,不論怎麼抵達(一次載 500 筆或分五次載 100 筆),畫出來都一樣。它否決「凍結第一頁版面、只替新列排版」,正因為那會讓版面變成路徑相依。

虛擬化碰的是另一個函數。把重繪拆成兩段:

1. `layout = graph.loadCommits(整份載入清單)` —— vertex 的 lane、branch、顏色。這一段**不變**,仍然每次清空、對整份清單重算。
2. `document 裡的列 = 視窗(layout, 捲動位置, 列高)` —— 這是虛擬化新增的。

性質要的是 1 是純函數。2 本來就依賴捲動位置,但它只決定**畫出哪些列**,從不回頭影響 1。所以「切到別的分頁再切回來,同一份歷史畫出不同的圖」不會發生:視窗不同,畫出的那幾列仍是同一份 layout 的切片。原型的對齊量測(第 9940 列,0.2 px)就是這件事在像素上的樣子。

**不相容的版本長這樣,實作時必須擋掉:**

- **只對視窗內的列跑版面走訪。** 看起來是順手的優化,但 lane 與顏色取決於上方所有列的歷史,只算可見的部分會讓結果依賴「從哪裡開始算」—— 這正是 ADR-0020 否決的路徑相依,換一個入口回來。而且它也沒什麼可省:走訪在 3000 筆只有 3.2 ms。
- **讓 layout 讀 DOM。** 今天 `renderGraph` 用 `tableElem.children[0].clientHeight` 推 `grid.y`。那是**幾何**輸入不是拓撲,不影響 lane 與顏色;但虛擬化之後表格高度是 spacer 撐出來的,這一讀會變成循環(spacer 高度依賴列高,列高從表格高度推)。列高要改成量一列、或從 CSS 讀常數,與 `frozenHeaderHeight` 從 `scroll-margin-top` 讀值的做法同一個模式。

所以實作若做出來,ADR-0020 不需要被 supersede;它值得補一條後果:「虛擬化只決定哪些列在 document 裡,版面走訪仍然對整份載入清單做」。若哪天有人想做第一個「不相容的版本」,那才是要寫新 ADR 取代 0020 的時候。

順帶一提,虛擬化對 ADR-0020 處理的另一半(後端每次整份重抓)沒有任何影響。兩者正交。

## 已知限制,逐項

每一項標出改動大小。「小 / 中 / 大」以今天的程式碼為準。

### ADR-0014 鍵盤導覽 —— 中,而且是前提

今天的鍵盤全部建立在「每一列都在 DOM 裡」:`graphRows()` 取整張表、`focusedRowIndex` 用 `indexOf`、`moveRowFocus` 對陣列做 `stepWithinGroup`、`expandedCommit.srcElem` 存的是一個 DOM 節點。

虛擬化之後:

- 移動要改成對 **commit 索引** 做,再「確保目標列已渲染 → focus」。從視窗最後一列按 Down,目標可能還不在 DOM 裡。
- **持有焦點的列必須被釘在 document 裡。** Page Up / Page Down 只捲動、不移焦點(ADR-0014 的刻意設計),捲遠了視窗會移走,持有焦點的那一列一被移除,焦點就掉到 `body`,下一次方向鍵從第一列開始 —— 正是 ADR-0019 描述過的那個「人在第 1 列」的故障,換條路回來。解法是視窗永遠包含焦點列(或在它旁邊留一個釘住的列)。
- roving tabindex 的唯一 tab stop 也是同一件事:它所在的列不能被回收。
- 焦點跨重繪存活已經是用 hash 當身分(`focusedRowKey` / `graphRowKey`),這個 seam 可以直接沿用;要改的只是「找回同一個身分」時先確保它被渲染。
- 好處是方向鍵的 O(N) 也一起消失(10000 筆時 17 ms → 與視窗大小成正比)。

`Home` / `End`(ADR-0014 說未做)在虛擬化後會更值得補,因為瀏覽器原生的捲到頂底仍然有效(spacer 撐出了真實的頁高),但沒有任何鍵能把**焦點**送到最後一列。

### Find 與 `scrollIntoView` —— 中,面最廣

`main.ts` 裡實際呼叫 `scrollIntoView` 的有 7 處,其中 5 處的對象是**任意一列 commit**:Find 的目前匹配、Locate HEAD、捲到 stash、CDV 裡點 parent hash、方向鍵移動焦點(`focusGraphMember`)。另外 inline CDV 的 auto-centre 是手算捲動,一樣以列的 DOM 位置為準。每一處今天都是「找到列 → 捲過去」;虛擬化後每一處都得變成「用索引算出位置 → 捲過去 → 等視窗更新 → 找到列」。

最乾淨的形狀是**一個**入口(例如 `revealRow(index, block)`),用 `列高 × 索引 + frozenHeaderHeight()` 算捲動位置。webview 已經有手算捲動的先例並且從 `scroll-margin-top` 讀表頭高度,所以這不是新模式,是把這 6 處收斂到一處。

Find 的高亮也要換方向:今天是畫完再走 DOM 補 class(`applyFindHighlights`,10000 筆 19 ms);虛擬化後要在**產生列的時候**就依 `findMatches` 帶上 class,否則捲進視窗的新列沒有高亮。VS Code 自己的 webview 尋找(`enableFindWidget`)本專案沒有開,所以不用擔心原生尋找找不到未渲染的列。

### 凍結表頭(#206)—— 小

原型直接驗證過:表頭列放在上方 spacer 之前,`th` 的 `position: sticky` 照常黏在 32 px,`scroll-margin-top` 照常讓列停在表頭下方。`inFrozenHeader` 的規則不受影響。唯一要注意的是表頭列必須永遠留在 `<tbody>` 的第一列,不能被視窗化掉。

### 欄寬 —— 中,而且是產品決定

`autoLayout` 是出貨預設,而它的欄寬隨「目前渲染的列」變動,已量到會跳(見上)。虛擬化需要固定欄寬,選項:

1. 永遠 `fixedLayout`,欄寬在每次重繪時從**整份清單**算(例如用 canvas `measureText` 量日期與作者欄的最大寬,或乾脆用固定預設寬)。
2. 只在虛擬化啟用時切到 `fixedLayout`。

今天 `fixedLayout` 只在使用者拖過欄寬之後才出現,所以兩者都是**使用者看得見的改變**:第一次打開的欄寬會與今天不同。這要 maintainer 拍板,不該在實作票裡默默決定。

### inline Commit Details View 列 —— 中

inline CDV 是插在展開那列後面的一個 `<tr>`,高度不固定(ADR-0019 量到 253 px),`renderGraph` 用 `expandY` 把它下方的 vertex 往下推。虛擬化後:

- spacer 與「索引 → 位置」的換算要把 `expandY` 加在展開列之後的所有列上。這是一個加法,不難,但每一個手算捲動的地方都要經過同一個函數,否則會差一個 CDV 的高度 —— 而那正是 ADR-0019 花了一整段在追的同一種跳動。
- **展開的 CDV 不能被視窗化掉。** 它有自己的狀態:檔案清單的捲動位置、檔案清單的鍵盤焦點(ADR-0019 立法要求焦點跨重繪存活的第二個群組)、auto-centre 記住的身分。被移除再重建,三樣都會丟。所以它與焦點列一樣要被釘住。
- docked 的 CDV 是 `position: fixed`,不在文件流內,不受影響;它的 `scroll-margin-bottom`(#217)照舊。

### 圖形 SVG —— 第一步可以不動

SVG 在 2026-08 報告裡佔一次重繪的 2.3% + 5.3%。原型量到「保留整份 SVG、只視窗化表格」在 10000 筆是 76.9 ms,仍是現況的 1/24,而且**不用碰 `graph.ts`**。

要連 SVG 一起視窗化,`Graph.render()` 要能接一個列範圍:vertex 好切(一列一個 circle),path 不好切 —— 一條 branch 是一條跨很多列的 `<path>`,要在 segment 層級裁切。這是 `graph.ts` 內部的改動,而 `graph.ts` 有 ADR-0020 的最小重現測試在守。值得放在第二步,而且只在第一步之後還量得到 SVG 是瓶頸時才做。

### 頁尾與自動載入(ADR-0019)—— 小

頁尾(載入更多、重設入口、計數)在 `#footer`,不在表格裡。spacer 讓頁面高度與今天完全相同(72,103 對 72,102 px),所以頁尾的位置、自動載入的「距底 250 px」門檻、`getPageHeight` 的快取都不受影響。頁尾控制項的焦點身分本來就用 id,不用改。

### 無障礙 —— 小,但不能漏

`role="grid"` 的列被視窗化後,螢幕閱讀器只看得到 120 列。需要在 grid 上補 `aria-rowcount`、在每列補 `aria-rowindex`。

## 建議

**先做一部分。** 分三張票,前一張是後一張的前提,每一張單獨出貨都不會讓任何東西變差:

1. **讓列的身分與位置不依賴 DOM。** 鍵盤、焦點還原、Find 高亮、`expandedCommit.srcElem`、那 6 處對圖形列的捲動收斂到「commit 索引 + 一個 `revealRow` 入口」。視窗仍然是全部列,所以行為不變、jsdom 測試照舊。單獨的收益:方向鍵與 Find 的 O(N) 消失。**這張是成本的大頭,也是決定可不可行的那一張** —— 做完它,虛擬化本身就只剩下一個「視窗 = 全部 / 一段」的開關。
2. **表格列的固定列高視窗化,超過門檻才縮小視窗。** SVG 不動。需要先由 maintainer 決定欄寬那一項。焦點列與 inline CDV 釘住。補 `aria-rowcount` / `aria-rowindex`。在 ADR-0020 補一條後果(見上)。
3. **(可選)SVG 視窗化。** 只在 2 之後還量得到它是瓶頸時。

**不建議:** `content-visibility`(量過無效)、分批漸進渲染(收益一半、麻煩一樣多)、以及任何「只對可見列跑版面走訪」的變體(違反 ADR-0020)。

**如果 maintainer 決定不做:** 這也站得住。出廠 300 筆沒有任何問題;代價只由撐大視窗的使用者付,而重設入口是他們的出路。那樣的話,至少值得把 1 裡面「方向鍵 O(N)」那一小塊單獨修掉 —— 它與虛擬化無關,10000 筆時按住 Down 已經吃掉一整幀。

## 量測不足之處

- **機器負載很高(70–97%)。** 絕對值有大幅漂移(3000 筆的 blocking task 379–591 ms),偶有數秒級的離群值(GC 或排程)。結論建立在倍數上(現況 vs 原型差 20–100 倍),那個量級遠大於漂移。
- **記憶體幾乎沒量到。** `usedJSHeapSize` 跨回合在 2.4–36 MB 之間亂跳,而且原型本身為了重用 markup 而把 N 列的字串留在 JS heap 裡,污染了比較。也沒有 cross-origin isolation 可用 `measureUserAgentSpecificMemory`。唯一可信的記憶體指標是節點數:**71,560 → 953**。
- **paint / composite 只在「到下一幀」與捲動幀間隔裡間接出現。** 沒有逐段歸因。
- **原型的 SVG 視窗化是近似。** 只刪了視窗外的 circle,path 整條保留;在 lane 很多的拓撲(2026-08 的 `wide`)裡 path 會比這裡多,這一項會被低估。
- **原型沒有實作鍵盤、Find、CDV。** 那些項目的改動大小是讀程式碼估的,不是做出來的。
- **完整重繪的「虛擬化後」數字是估計**(原型的 DOM 成本 + 2026-08 報告的純 JS 成本),沒有端到端跑過。
- **合成歷史,不是真存放庫。** 欄寬抖動在真實資料上只會更大;列高固定這個前提則與資料無關(`line-height: 24px` + `nowrap`)。
- **Chromium 152,不是 VS Code 搭的版本。** 2026-08 報告用的是與 VS Code 1.134 同主版本的 148;這次的瀏覽器窗格已經升版。兩份報告的絕對值不要直接相減。
